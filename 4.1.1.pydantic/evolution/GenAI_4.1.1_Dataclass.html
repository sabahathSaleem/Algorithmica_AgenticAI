Section 01

Core Concepts

Every building block introduced across these 3 files — pure Python, no frameworks.

🏛️

Classical Python Class

The traditional way to define a data-holding class. You manually write __init__ to set attributes, __repr__ to control printing, and __eq__ to define equality. Verbose but fully explicit.

class Product: …
⚡

@dataclass Decorator

A Python built-in decorator (since 3.7) that auto-generates __init__, __repr__, and __eq__ from your field annotations. Same result as the classical version — with a fraction of the code.

from dataclasses import dataclass
🧙

Dunder Methods (Magic Methods)

Methods with double underscores: __init__, __repr__, __eq__. Python calls them automatically — Product(…) calls __init__, print(p) calls __repr__, p1 == p2 calls __eq__. You never call them directly.

called by Python, not you
🎨

Python Decorator

A decorator (@something) is a function that wraps another function or class to add behaviour. @dataclass inspects your class's annotations and injects methods into it at definition time. The class is transformed before your code even runs.

@dataclass transforms the class
🏷️

Type Annotations (Hints)

name: str is a type hint — it documents the expected type. In plain Python, they are ignored at runtime — you can pass an int where str is expected and Python won't complain. Type hints are for tools (IDEs, mypy), not execution.

hints ≠ enforcement
⚠️

The Critical Gotcha

File 3 proves it: Product(12, 2, 300) — passing an int for name: str — works silently. No error. The dataclass stores 12 happily. This is Python's design. To get enforcement, you need Pydantic (which is exactly what pydantic_ai uses under the hood).

use Pydantic for validation!
💡 Why These 3 Files Matter for GenAI

These are the Python OOP foundations that pydantic_ai's BaseModel is built on. When you wrote class ProfileInfo(BaseModel) in Week 5, you were doing the same thing — defining a data schema. But Pydantic's BaseModel goes further: it actually enforces type hints at runtime (unlike the plain @dataclass in File 3). Understanding the difference between a plain class, a dataclass, and a Pydantic model is essential for knowing what to use when.

Section 02

The 3 Dunder Methods Explained

Written manually in File 1, auto-generated by @dataclass in Files 2 & 3.

__init__(self, …)
Triggered by: Product("Laptop", 3, 200)
The constructor — called automatically when you create a new instance. Sets up instance attributes (self.name, self.quantity, self.price). Without it, Product("Laptop", 3, 200) would fail with a TypeError.
✓ auto-generated by @dataclass
__repr__(self)
Triggered by: print(p1) → str(p1)
The string representation. Called by print(), str(), the REPL, and debuggers. Without it, you'd see <__main__.Product object at 0x7f...> — useless. File 1 returns a custom string. @dataclass generates Product(name='Laptop', quantity=3, price=200).
✓ auto-generated by @dataclass
__eq__(self, other)
Triggered by: p1 == p3 → True/False
The equality comparator. Without it, p1 == p3 compares memory addresses (always False for different objects, even if identical!). File 1 compares all three fields manually. @dataclass auto-generates field-by-field comparison.
✓ auto-generated by @dataclass
🔍 Dunder Order Matters — print() Internals

When you call print(p1), Python internally runs: p1.__str__() → if not defined, falls back to p1.__repr__(). File 1's classical class defines __repr__ (not __str__), so print uses that as fallback. The print("Product.__repr__ called") inside the method proves this — it fires when you print(p1) even though you called print, not repr.

🧠 Default __eq__ Without @dataclass

By default, Python's == on objects checks identity (same memory address), not equality (same content). Two objects with identical data are at different addresses → p1 == p3 returns False without a custom __eq__. This is the same as p1 is p3. Both @dataclass and File 1's manual implementation override this to compare field values.

Section 05

The Type Hint Gotcha — File 3

product_dataclass2.py is a deliberately broken test — and everything "works". That's the warning.

⚠️ Critical Python Behaviour

Type annotations like name: str in a dataclass are documentation only. Python's runtime does NOT enforce them. If you pass the wrong type, no error is raised. The wrong value is stored silently. This surprises everyone coming from typed languages like Java or TypeScript.

Declared type: name: str
p2 = Product(12, 2, 300)
⚠ No error. Stores 12 as name.
An integer where a string was expected — Python doesn't care. p2.name returns 12.
Declared type: quantity: int
p3 = Product("Laptop", "3", 200)
⚠ No error. Stores "3" as quantity.
A string where an int was expected. p3.quantity is "3" (string), not 3 (int). This will crash later if you do math on it.
Declared type: price: float
p1 = Product("Laptop", 3.5, 200)
✓ Works. int 3.5 ≈ float.
quantity: int but 3.5 (float) is passed. No error — stored as-is. The hint is just decoration.

🔗 The Connection to pydantic_ai

File 3's Product(12, 2, 300) silently storing wrong types is exactly why pydantic_ai's output_type= uses Pydantic BaseModel, not @dataclass. When the LLM returns experience_years: "five" (a string) instead of an integer — a Pydantic model raises ValidationError and pydantic_ai retries the call. A plain dataclass would silently store the string and your code would crash later. That's the difference between a demo and a production system.

Commented Code — All 3 Files

Every dunder, decorator, and type annotation explained with the reasoning behind it.

product_classical.py MANUAL DUNDER METHODS 
class Product:
        # A plain Python class — no inheritance, no decorators.
    # To make it usable (printable, comparable), we must write 3 dunder methods.
    # Python calls these automatically in specific situations.

    def __init__(self, name: str, quantity: int, price: float):
                # __init__ = constructor, called when: Product("Laptop", 3, 200)
        # 'self' = the new object being created
        # name: str, quantity: int, price: float → TYPE HINTS — documentation only,
        # NOT enforced. Python won't error if you pass int for str.

        print("Product.__init__ called")
                # This print is for learning — proves when the constructor fires.
        # In real code, you wouldn't have this.

        self.name = name
        self.quantity = quantity
        self.price = price
                # self.x = val → stores values as instance attributes.
        # Now p1.name, p1.quantity, p1.price are accessible from outside.


    def __repr__(self):
                # __repr__ = string representation.
        # Called by: print(p1), str(p1), repr(p1), debugger, REPL.
        # Without this: print(p1) shows <__main__.Product object at 0x7f...>
        # Must return a STRING — not print it.

        print("Product.__repr__ called")
        return self.name + " " + str(self.quantity) + " " + str(self.price)
                # Custom format: "Laptop 3 200"
        # str(quantity) and str(price) because you can't concatenate int/float to str.
        # @dataclass's auto format would be: "Product(name='Laptop', quantity=3, price=200)"


    def __eq__(self, p):
                # __eq__ = equality operator, called by: p1 == p2
        # 'p' is the other object being compared.
        # Without this: p1 == p3 compares MEMORY ADDRESSES → always False
        # for two different objects (even if all fields are identical!)
        # We want value-based equality: same fields = same object logically.

        print("Product.__eq__ called")
        return (
            self.price == p.price
            and self.quantity == p.quantity
            and self.name == p.name
        )
                # All 3 fields must match for equality.
        # Python's 'and' short-circuits: if price differs, stops immediately.
        # Parentheses for multi-line expression — style, not required.


# ─── CREATING INSTANCES ────────────────────────────────────────────────────
p1 = Product("Laptop", 3, 200)   # → fires __init__ → prints "Product.__init__ called"
print(p1)                        # → fires __repr__ → prints "Laptop 3 200"
p2 = Product("LED", 2, 300)
print(p2)
p3 = Product("Laptop", 3, 200)   # same values as p1, but DIFFERENT object in memory
print(p3)
print(p1 == p3)   # → fires __eq__ → compares fields → True (same values)
print(p1 == p2)   # → fires __eq__ → price 200 ≠ 300 → False
product_dataclass1.py AUTO-GENERATED DUNDERS 
from dataclasses import dataclass
# 'dataclasses' is a Python STANDARD LIBRARY module (no pip install needed).
# 'dataclass' is a decorator function imported from it.

@dataclass
# This is a DECORATOR — applied to the class below it.
# What it does at class-definition time:
#   1. Reads all field annotations (name: str, quantity: int, price: float)
#   2. Generates __init__(self, name, quantity, price): self.name = name; ...
#   3. Generates __repr__(self): return f"Product(name={self.name!r}, ...)"
#   4. Generates __eq__(self, other): return (self.name,...) == (other.name,...)
# The class is TRANSFORMED before your code runs at all.
class Product:
    name: str
    quantity: int
    price: float
        # These 3 lines are FIELD DECLARATIONS — not just hints.
    # @dataclass uses them as the blueprint for __init__ and __repr__.
    # The ORDER matters: __init__ takes params in this order.
    # These are equivalent to self.name = name in __init__.

# ─── EXACTLY THE SAME USAGE AS FILE 1 ─────────────────────────────────────
p1 = Product("Laptop", 3, 200)
print(p1)    # → Product(name='Laptop', quantity=3, price=200)
              #   Note: @dataclass format, not "Laptop 3 200"
p2 = Product("LED", 2, 300)
print(p2)
p3 = Product("Laptop", 3, 200)
print(p3)
print(p1 == p3)   # → True  (auto __eq__ compares field tuples)
print(p1 == p2)   # → False

# RESULT: identical behaviour to product_classical.py
# with 13 fewer lines of boilerplate code.
# No print("...called") messages — the dunders are silent and generated.
# The ONLY visible difference: __repr__ format is more descriptive.
product_dataclass2.py TYPE HINT GOTCHA 
from dataclasses import dataclass

@dataclass
class Product:
    name: str       # declared as string
    quantity: int   # declared as integer
    price: float   # declared as float
# Identical class to dataclass1. Now we create instances with WRONG types.


p1 = Product("Laptop", 3.5, 200)
# quantity declared as int, but 3.5 (float) is passed.
# Expected: TypeError or some warning.
# Actual: WORKS SILENTLY. p1.quantity = 3.5 (a float stored as "quantity")
# Python doesn't check. No error. No warning. The hint is ignored.
print(p1)
# Output: Product(name='Laptop', quantity=3.5, price=200)
# ← 3.5 printed for quantity — proof the float was stored


p2 = Product(12, 2, 300)
# name declared as str, but 12 (integer) is passed.
# Again: WORKS. p2.name = 12 (an integer stored as "name").
# This is the most dangerous case — now if code does p2.name.upper()
# it would crash with AttributeError: 'int' object has no attribute 'upper'
# The bug is hidden until some other code tries to USE the name field.
print(p2)
# Output: Product(name=12, quantity=2, price=300)
# ← 12 in the name position — proves the int was stored


p3 = Product("Laptop", "3", 200)
# quantity declared as int, but "3" (string) is passed.
# p3.quantity = "3" (string). No error.
# Now if code does: total_value = p3.quantity * p3.price
# → "3" * 200 → "3" repeated 200 times → SILENT BUG, not a crash!
# (In Python, "3" * 200 = "333...333" — string repetition)
print(p3)
# Output: Product(name='Laptop', quantity='3', price=200)
# ← '3' in quotes — proves the string was stored as quantity

# ─── LESSON ────────────────────────────────────────────────────────────────
# Type hints in plain Python (including @dataclass) are:
#   ✓ Useful for IDEs (autocomplete, warnings)
#   ✓ Useful for static analysis tools (mypy, pyright)
#   ✓ Useful as documentation
#   ✗ NOT enforced at runtime
#   ✗ Will NOT raise errors for wrong types
#
# To get runtime enforcement, use:
#   → Pydantic BaseModel  (used in pydantic_ai's output_type=)
#   → @dataclass(validate_fields=True) in Python 3.10+ (limited)
#   → Manual validation in __post_init__
