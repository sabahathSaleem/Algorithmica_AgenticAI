Section 01

Core Concepts

Everything new introduced across these 3 files — the Pydantic validation layer in full.

🔄

Type Coercion (Auto-Cast)

Pydantic doesn't just validate — it coerces. If you pass "3" for an int field, Pydantic silently converts it to 3. This is intentional for parsing JSON/API data where numbers often arrive as strings. It succeeds when conversion is lossless and safe.

"3" → 3 (string→int coercion)
🚫

ValidationError — Hard Failure

When Pydantic cannot safely coerce a value — e.g. 3.5 for int (lossy: drops the .5) — it raises a ValidationError. This is a hard stop: your code never receives an invalid object. The error has rich detail: which field, what value, why it failed.

3.5 → int fails (lossy!)
🛡️

try / except ValidationError

The production pattern for handling Pydantic errors. Wrap model creation in try: — if validation fails, Pydantic raises ValidationError and the except: block catches it cleanly. Your app doesn't crash; you log/display the error and continue.

graceful degradation
📦

** Dictionary Unpacking

Product(**data) where data is a dict: the ** operator unpacks key-value pairs as keyword arguments. {"name": "Laptop", "quantity": 3} becomes Product(name="Laptop", quantity=3). Essential for parsing API responses, JSON payloads, and LLM output.

**dict → keyword args
🌐

external_data Pattern

File 3 names the dict external_data — a hint that this dict could come from anywhere: a REST API response, a database row, a user form submission, or an LLM's JSON output. Pydantic's job is to validate and normalise it before your business logic ever sees it.

API / DB / LLM → validated object
⚡

Lossless vs Lossy Coercion

Pydantic's coercion rule: lossless = OK, lossy = error. "3" → int(3): no data lost ✓. 3.5 → int(3): the .5 is dropped — lossy ✗. "abc" → int: impossible ✗. This rule makes Pydantic predictable and trustworthy.

lossless ✓ lossy ✗

Pydantic's BaseModel enforces types — but with intelligence: it first tries to coerce (File 1), then raises a hard error if coercion is lossy (File 2), and finally shows you the production pattern for external data (File 3). Section 03

Pydantic's Coercion Rules — What Converts, What Fails

Pydantic v2 tries to coerce before it rejects. Here's exactly when it succeeds and fails.

Value PassedField TypeResultPydantic ActionFile
"3" (str)int ✓ Stored as 3 Coercion: int("3") = 3. Lossless → allowed. File 1
3.5 (float)int ✗ ValidationError Coercion: int(3.5) = 3. Drops .5 → lossy → rejected. Files 2, 3
3 (int)float ✓ Stored as 3.0 Widening: int fits in float with no loss. Allowed. All files
"Laptop" (str)str ✓ Stored as "Laptop" Exact match. No coercion needed. All files
12 (int)str ⚠ Stored as "12" Pydantic coerces int to str: str(12) = "12". Allowed in v2 lax mode. (extension)
"abc" (str)int ✗ ValidationError int("abc") raises ValueError. Cannot coerce → ValidationError. (extension)
Noneint ✗ ValidationError None is not numeric. Use Optional[int] to allow None. (extension)
🔑 The Lossless Rule — Key Mental Model

Ask yourself: "Can I convert this value back to the original without losing information?"
"3" → 3 → "3": round-trip works. Lossless ✓
3.5 → 3 → 3.5: round-trip fails, .5 is gone. Lossy ✗
Pydantic uses a similar logic (not exactly round-trip, but precision-preserving). This makes it safe for financial data, IDs, and any domain where silent rounding would be catastrophic.

Section 04

try / except ValidationError

The correct way to handle Pydantic failures — don't let your app crash.

Execution Flow in validation2.py
TRY BLOCK — "happy path"
p1 = Product(name="Laptop", quantity=3.5, price=200)
← 3.5 (float) for int field
← Pydantic detects lossy coercion
→ raises ValidationError immediately
print(p1) never reached
p2 = Product(...) never reached
all remaining lines skipped
EXCEPT ValidationError as e
print(e)
← e is the ValidationError object
← print(e) shows formatted error details
← execution continues after this block
app doesn't crash
→
IF all valid:
All lines in try run normally. Products created, printed, compared. except block skipped.
IF validation fails (our case):
Execution jumps to except at the first failing line. ValidationError printed. App continues safely after the try/except block.
⚡ Why try/except Here and Not in File 1?

File 1 has no try/except because quantity='3' succeeds via coercion — no error to catch. File 2 uses quantity=3.5 which fails — so we need error handling. In production, you'd always wrap external data parsing in try/except because you can't trust the input. File 3's pattern is the gold standard: every real-world data ingestion point should be protected.

⚠️ The Entire try Block Exits on First Error

Notice: p2 and p3 are created after p1 in the try block. When p1 fails, Python immediately jumps to the except block — p2 and p3 are never created. The print statements after p1 are also never reached. This is Python's standard try/except flow, not Pydantic-specific. To collect all errors, create each object in its own try/except.

What the error message tells you — and how to read it in production logs.

4   [type=int_from_float, input_value=3.5, input_type=float] ← error type, the bad value, the type it had
5   For further information visit https://errors.pydantic.dev/... ← doc link for this specific error type
field name

Which field failed. Use this to tell users exactly what to fix.
input_value
3.5
The exact bad value received. Critical for debugging API inputs.
input_type

The type Pydantic received. Tells you where the data came from (float vs str).
error type
int_from_float
Machine-readable error code. Use e.errors() to get this as structured data.
🔍 Getting Structured Error Data

print(e) gives a human-readable string. But in production code you'd use:
e.errors() → returns a list of dicts, one per failed field. Machine-readable — perfect for building API error responses or logging to a dashboard.
e.error_count() → total number of validation failures (one model can have multiple).
This is why Logfire (Week 4) captures Pydantic errors so richly — it reads e.errors() directly.

Section 07

Commented Code — All 3 Files

Every coercion, every error path, every pattern explained.

validation1.py COERCION — SILENT SUCCESS 
from pydantic import BaseModel
# Pydantic v2 BaseModel. Fields are type-annotated below.
# Unlike @dataclass, Pydantic ENFORCES types — but with coercion first.

class Product(BaseModel):
    name: str
    quantity: int
    price: float
        # Identical to the @dataclass in 4.1.1.
    # BUT: Pydantic validates and coerces values at creation time.
    # No Field() here — just raw type annotations.
    # Pydantic knows: int field → try to convert input to int.
    # float field → int 200 is coerced to 200.0 automatically.


p1 = Product(name="Laptop", quantity=3, price=200)
# All correct types. price=200 (int) coerced to 200.0 (float) — lossless.
# Note: using keyword args here (name=..., quantity=...) not positional.
# Pydantic requires keyword args by default (unlike @dataclass).
print(p1)
# Output: name='Laptop' quantity=3 price=200.0
# Pydantic's __repr__: shows field names WITH values, quoting strings.

p2 = Product(name="LED", quantity=2, price=300)
print(p2)

p3 = Product(name="Laptop", quantity='3', price=200)
# quantity='3' — a STRING where int is declared.
# @dataclass would: store '3' silently as a string (bug!).
# Pydantic does: attempt int('3') = 3. Lossless → SUCCEEDS.
# p3.quantity = 3 (integer), NOT '3' (string).
# No exception raised. No error. Silent coercion.
# This behaviour is designed for JSON APIs where numbers arrive as strings.
print(p3)
# Output: name='Laptop' quantity=3 price=200.0
# Notice quantity=3 (int), NOT quantity='3' (str) — Pydantic converted it.

print(p1 == p3)
# True — because after coercion, both have quantity=3 (int).
# If @dataclass stored '3': p1.quantity==3 (int) != p3.quantity=='3' (str)
# Pydantic's coercion made the equality work correctly.
print(p1 == p2)
# False — different name, quantity, price.
validation2.py HARD FAILURE + try/except 
from pydantic import BaseModel, ValidationError
# ValidationError is Pydantic's exception class.
# Must be imported separately to use in except clause.
# It's a subclass of ValueError — but much richer (has .errors(), .error_count()).

class Product(BaseModel):
    name: str
    quantity: int
    price: float


try:
        # ← try block: wrap ALL model creation in here.
    # Python executes these lines one by one.
    # The FIRST ValidationError exits the try block immediately.

    p1 = Product(name="Laptop", quantity=3.5, price=200)
        # quantity=3.5 — FLOAT for int field.
    # Pydantic attempts: int(3.5) = 3. BUT .5 is dropped → LOSSY.
    # Pydantic REFUSES the coercion and raises ValidationError here.
    # Key distinction from File 1:
    #   '3' → 3: lossless  → coercion allowed ✓
    #   3.5 → 3: lossy     → coercion rejected, ValidationError ✗

    print(p1)        # ← NEVER REACHED (exception raised on line above)
    p2 = Product(name="LED", quantity=2, price=300)   # ← NEVER REACHED
    print(p2)        # ← NEVER REACHED
    p3 = Product(name="Laptop", quantity=3, price=200)   # ← NEVER REACHED
    print(p3)        # ← NEVER REACHED
    print(p1 == p3) # ← NEVER REACHED
    print(p1 == p2) # ← NEVER REACHED

except ValidationError as e:
        # Catches ONLY ValidationError (not other exceptions).
    # 'e' is the ValidationError object — rich error data inside.
    # e.errors()      → list of dicts, one per failure
    # e.error_count() → total number of field failures
    # str(e)          → human-readable summary (what print(e) shows)
    print(e)
        # Prints the full validation error summary.
    # Shows: error count, field name, human message, type code, bad value.
    # App continues normally after this block — no crash.
validation3.py REAL-WORLD PATTERN — ** UNPACK 
from pydantic import BaseModel, ValidationError

class Product(BaseModel):
    name: str
    quantity: int
    price: float


try:
    external_data = {
        "name": "Laptop",
        "quantity": 3.5,
        "price": 200
    }
        # external_data is a plain Python dict.
    # The name 'external_data' signals this represents data from OUTSIDE
    # the application: a REST API response, a database row, a JSON file,
    # form submission, CSV row, or LLM output.
    # It contains 3.5 for quantity — same bad value as File 2.

    p1 = Product(**external_data)
        # **external_data = "unpack this dict as keyword arguments".
    # Equivalent to:
    #   Product(name="Laptop", quantity=3.5, price=200)
    #
    # Python expands the dict: each key becomes a parameter name,
    # each value becomes the argument.
    # This is how ALL of these work:
    #   pydantic_ai LLM output → Product(**llm_json)
    #   FastAPI request body   → Product(**request.dict())
    #   CSV row parsing        → Product(**row)
    #   database record        → Product(**db_row._asdict())
    #
    # Pydantic validates: quantity=3.5 → int field → lossy → ValidationError.

    print(p1)   # ← NEVER REACHED

except ValidationError as e:
    print(e)
        # Same output as File 2 — the error is identical because the bad
    # data is identical. The pattern (dict → unpack → validate) is the
    # real lesson, not the specific error.
    #
    # IN PRODUCTION you'd log this, return an HTTP 422, or retry:
    #   import logging
    #   logging.error(f"Invalid product data: {e.errors()}")
    #   return {"error": "Invalid input", "details": e.errors()}
🚀 The Full Connection to pydantic_ai

When you write Agent(output_type=ProfileInfo), pydantic_ai internally does exactly File 3's pattern every time the LLM responds:

llm_json = {"name": "John", "experience_years": 5, "skills": [...]}
result = ProfileInfo(**llm_json) # ← Pydantic validates!

If the LLM returns "experience_years": "five" — Pydantic raises ValidationError and pydantic_ai retries the call with the error as feedback to the LLM. That's the closed-loop validation you saw in Week 5 — and now you understand every layer of how it works.
