Section 01 — 🧠 Big Ideas

What Are We Learning?

Six new ideas — explained simply. No jargon. Promise.

🪆

Nested Models

A Pydantic model can have a field whose type is another Pydantic model. Like a box inside a box. A Restaurant contains Food objects. Each Food is itself validated. They stack as deep as you want.

model inside model ✓
📋

List[SomeModel]

List[Food] means: a list where every item must be a valid Food. You can have zero items, one, or a hundred. Pydantic validates each item individually. One bad item → error for that item, not a silent skip.

list of validated items
🤷

Optional[X] = None

Means: this field is not required. If you don't provide it, it defaults to None. Like a form field that says "Website (optional)". Works the same as Union[X, None] — can be the type OR nothing.

can be missing — that's OK
📧

EmailStr — Smart Validator

A special type from Pydantic that checks: does this string look like a real email? "john@" → error. "notanemail" → error. "john@example.com" → ✅. Built-in, no regex needed!

must be valid email format
➕

PositiveInt

An integer that must be greater than zero. 0 → error. -5 → error. 50 → ✅. Makes sense for number_of_seats — a restaurant with 0 or negative seats makes no sense!

int > 0 enforced
🌐

HttpUrl

A type that validates a URL — checks it starts with http:// or https://, has a real domain, etc. "tastybites" → error. "http://tastybites.com" → ✅. No need to write your own URL checker!

valid URL enforced

🧱 Why Separate Models Instead of One Big One?

You could put all fields flat in one giant Restaurant class. But separating into Food, Employee, Address etc. means:
1. Reuse — Address can be used in Employee, Customer, Order too.
2. Clarity — each model has one job.
3. Validation per level — if an Employee's email is wrong, Pydantic tells you exactly: "employees → index 1 → email → invalid".
This is exactly how real apps like Instagram, Uber, and Swiggy structure their data!

Section 03 — 🤷 Optional Fields

Optional — "This Field Is Not Required"

Some data is always there. Some might be missing. Optional handles the "might be missing" case.

✅ With ingredients (provided)
Food(
  name="Cheese Pizza",
  price=12.50,
  ingredients=["Cheese", "Dough"]
)
food.ingredients → ['Cheese', 'Dough']
Works perfectly ✅
🤷 Without ingredients (skipped)
Food(
  name="Veggie Burger",
  price=8.99
  # ingredients not mentioned at all
)
food.ingredients → None
No error! Optional = OK to skip ✅
🍔 Think of it Like a Burger Order Form

Name: [required] — you MUST fill this in.
Price: [required] — must have a price.
Ingredients: [optional] — some restaurants don't list them. That's fine.

Optional[List[str]] = None means: "a list of strings, OR nothing. Default is nothing."
The = None part sets the default — so if you don't pass it, Pydantic fills in None automatically.

🧠 Quick Check — What does Optional[List[str]] = None mean?
A) The field is a required list of strings
B) The field can be a list of strings OR missing (defaults to None) ✅
C) The field must be None always
D) This is a syntax error
✅ Answer B — Optional makes the field skippable. = None is the default value when skipped. Pydantic won't complain if you don't provide it!
Section 04 — 🪄 The Dict Magic Trick

Passing Dicts Instead of Model Instances

This is a superpower — and both files use it everywhere!

When Pydantic expects a nested model, you can pass a plain dict instead.
Pydantic automatically converts the dict to the right model — validates it too!
You write:
"owner": {
  "name": "John Doe",
  "email": "john@example.com"
}
a plain dict
→
Pydantic creates:
Owner(
  name="John Doe",
  email="john@example.com"
)
validated Owner instance ✅
→
If email was wrong:
"email": "notanemail"
→ ValidationError!
owner → email: not valid
caught immediately ✅
💡 Why Is This Powerful?

In real apps, data comes from JSON (APIs, databases, files) — always as dicts, never as Python objects. Pydantic's ability to accept raw dicts and auto-convert them means you don't have to manually do:

owner_obj = Owner(name=data["owner"]["name"], email=data["owner"]["email"]) ← painful

Instead you just do: Restaurant(**data) and Pydantic handles ALL the nested conversions at every level automatically. This is exactly the **external_data pattern from the serialization files!

What does model_dump() look like for nested models?

Nested models become nested dicts — perfect for databases and APIs.

restaurant1.model_dump() →

{
  'name': 'Tasty Bites',
  'location': '123, Flavor Street',
  'foods': [ ← the List[Food] becomes a list of dicts
    {
      'name': 'Cheese Pizza',
      'price': 12.5,
      'ingredients': ['Cheese', 'Tomato Sauce', 'Dough']
    },
    {
      'name': 'Veggie Burger',
      'price': 8.99,
      'ingredients': None ← Optional field was not provided
    }
  ]
}
Section 05 — 🔒 Smart Built-in Types

Pydantic's Built-in Smart Validators

File 2 uses special types that do validation automatically — no Field() constraints needed.

EmailStr
📧 Must be a valid email address
Checks the format: needs an @, a domain, and a valid extension. Install: pip install pydantic[email]
✗ "john" ← no @
✗ "john@" ← no domain
✗ "@example.com" ← no name
✓ "john@example.com"
PositiveInt
➕ Must be an integer greater than 0
Shortcut for int with gt=0. Perfect for things that can't be zero or negative: seats, quantity, count.
✗ 0 ← zero is not positive
✗ -5 ← negative
✗ 1.5 ← not an integer
✓ 1, 50, 999
HttpUrl
🌐 Must be a valid HTTP/HTTPS URL
Validates that the string is a real web address with scheme, domain. Returns a special URL object (not just a string) with parts accessible.
✗ "tastybites"
✗ "ftp://tastybites.com"
✓ "http://tastybites.com"
✓ "https://www.site.co.in"
💡 Why Not Just Use str?

You could write email: str — but then "notanemail" would be accepted silently.
You could write number_of_seats: int — but then -10 seats would pass.

Pydantic's special types encode the rules of your domain into the type itself. The model declares what's valid — you don't write separate checking code. This is a core principle called "make invalid states unrepresentable".

Section 06 — 💻 Code Walkthrough

Both Files — Every Line Explained

We'll read it like a story — step by step.

complex-structure1.py NESTED MODELS + OPTIONAL 
from typing import List, Optional
# List    → tells Python "this field holds a list of something"
#           Before Python 3.9 you had to import it from typing.
#           Python 3.9+ you can write list[str] directly (lowercase l).
#           Here we use List[str] (uppercase) — both work the same.
# Optional → tells Python "this field can be X, or it can be None"
#             Optional[List[str]] = "a list of strings, or nothing"

from pydantic import BaseModel


# ─── INNER MODEL (defined FIRST because Restaurant uses it) ────────────────
class Food(BaseModel):
        # A food item on a menu. Think of each menu item as a Food object.

    name: str
    price: float

    ingredients: Optional[List[str]] = None
        # Breaking this down piece by piece:
    #   List[str]             → a list where every item is a string
    #   Optional[List[str]]   → that list, OR nothing at all
    #   = None                → default value is None (if not provided)
    #
    # So: you CAN provide ["Cheese", "Dough"], or you can skip it entirely.
    # Pydantic won't complain either way.
    # If you pass something that isn't a list of strings → ValidationError.


# ─── OUTER MODEL (uses Food inside it) ────────────────────────────────────
class Restaurant(BaseModel):
    name: str
    location: str
    foods: List[Food]
        # List[Food] = a list where every item must be a valid Food.
    # Pydantic will validate each item individually.
    # You can pass raw dicts — Pydantic converts them to Food objects!
    # If the list is empty [] that's valid too (zero foods is allowed).


# ─── CREATING THE RESTAURANT ──────────────────────────────────────────────
restaurant1 = Restaurant(
    name="Tasty Bites",
    location="123, Flavor Street",
    foods=[
                # Each item here is a plain DICT — not a Food object.
                # Pydantic sees List[Food] and auto-converts each dict to Food.
        {
            "name": "Cheese Pizza",
            "price": 12.50,
            "ingredients": ["Cheese", "Tomato Sauce", "Dough"],
                        # ingredients provided → stored as a List[str]
        },
        {"name": "Veggie Burger", "price": 8.99},
                # No ingredients here → Optional field → defaults to None
        # Pydantic doesn't complain. ingredients will be None for this food.
    ],
)

print(restaurant1)
# Output: name='Tasty Bites' location='123...' foods=[Food(name='Cheese Pizza', ...), Food(name='Veggie Burger', price=8.99, ingredients=None)]
# The dicts have been converted to Food objects inside the list!

print(restaurant1.model_dump())
# Returns the entire nested structure as plain Python dicts.
# Perfect for saving to MongoDB, returning from a FastAPI endpoint, etc.
# The Food objects become dicts, the List[Food] becomes a list of dicts.
complex-structure2.py ADVANCED NESTING + SMART TYPES 
from typing import List
from pydantic import BaseModel, EmailStr, PositiveInt, conlist, Field, HttpUrl
# EmailStr   → string that must be a valid email format
# PositiveInt → integer that must be > 0
# conlist     → a list with length constraints (imported but not used here — maybe for future use)
# Field      → add extra constraints/descriptions (we used this in Week 5 files)
# HttpUrl    → string that must be a valid HTTP/HTTPS URL


# ─── 3 SMALL MODELS (used inside Restaurant) ──────────────────────────────
class Address(BaseModel):
    street: str
    city: str
    state: str
    zip_code: str
        # Simple model for a postal address.
    # zip_code is str (not int) — keeps leading zeros like "01234"
    # and handles UK/Indian formats like "NW1 6XE", "400001"


class Employee(BaseModel):
    name: str
    position: str         # e.g. "Chef", "Waiter", "Manager"
    email: EmailStr
        # EmailStr validates the email format automatically.
    # "jane.doe@example.com" → ✅
    # "janedoe" → ✗ ValidationError: "value is not a valid email address"


class Owner(BaseModel):
    name: str
    email: EmailStr
        # Same EmailStr here — the owner's email must also be valid.
    # Owner and Employee both use EmailStr but are separate models
    # because an Owner is not the same concept as an Employee
    # (owner has different responsibilities, different fields potentially).


# ─── THE MAIN MODEL (uses all 3 above) ────────────────────────────────────
class Restaurant(BaseModel):
    name: str

    owner: Owner
        # A single Owner object (not a list — one restaurant has one owner).
    # Pass a dict like {"name": "John", "email": "..."} → auto-converted.

    address: Address
        # A single Address object.
    # Pass a dict with all 4 fields → auto-converted to Address.

    employees: List[Employee]
        # A list of Employee objects — can be many.
    # Each dict in the list is validated as an Employee.
    # If any employee has an invalid email → ValidationError with the index:
    # "employees → 1 → email → value is not a valid email address"

    number_of_seats: PositiveInt
        # Must be an integer AND must be > 0.
    # PositiveInt = int + ge=1 (greater than or equal to 1).
    # number_of_seats=0  → ✗ (0 is not positive)
    # number_of_seats=50 → ✅

    delivery: bool
        # True or False. Does this restaurant deliver?

    website: HttpUrl
        # Must be a valid URL starting with http:// or https://.
    # Pydantic parses it into a special URL object with .scheme, .host, .path.
    # "tastybites" → ✗
    # "http://tastybites.com" → ✅


# ─── CREATING THE RESTAURANT ──────────────────────────────────────────────
restaurant1 = Restaurant(
    name="Tasty Bites",

    owner={"name": "John Doe", "email": "john.doe@example.com"},
        # Plain dict → Pydantic converts to Owner(name=..., email=...)
    # EmailStr check runs: "john.doe@example.com" passes ✅

    address={
        "street": "123, Flavor Street",
        "city": "Tastytown",
        "state": "TS",
        "zip_code": "12345",
    },
        # Dict → Address object. All 4 fields required (no Optional here).

    employees=[
        {"name": "Jane Doe", "position": "Chef", "email": "jane.doe@example.com"},
        {"name": "Mike Roe", "position": "Waiter", "email": "mike.roe@example.com"},
    ],
        # List of 2 dicts → Pydantic converts each to Employee.
    # Both emails validated. 2 employees created successfully.

    number_of_seats=50,  # 50 > 0 → PositiveInt ✅
    delivery=True,        # bool value ✅
    website="http://tastybites.com",
        # HttpUrl validates this. Returns special URL object.
    # In model_dump(): appears as a string URL again.
)

print(restaurant1)
# Shows the entire nested structure — all sub-models shown inline.
# Owner, Address, Employees all fully expanded.

print(restaurant1.model_dump())
# Returns the entire nested structure as plain dicts — fully recursive!
# restaurant1.model_dump()["employees"][0]["email"] → 'jane.doe@example.com'
# Great for: MongoDB insert, FastAPI response, JSON serialisation.
