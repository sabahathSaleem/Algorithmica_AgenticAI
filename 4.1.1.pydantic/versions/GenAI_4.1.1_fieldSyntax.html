Pydantic Field() — Two Syntax Styles

Same Model, Two Ways
to Write It

product_v1.py uses the classic Field(...) style. product_v2.py uses the modern Annotated[type, Field()] style. Same validation, same output — but v2 is what Pydantic officially recommends today, and what you'll see in production codebases. Let's understand every difference.

Section 01

Core Concepts

Six new ideas introduced across these two files.

…

The Ellipsis ... — Required!

Field(...) uses Python's built-in Ellipsis object as the first argument. It's Pydantic's signal for "this field is required — no default". If you omit a field marked with ..., you get a ValidationError immediately. Think of it as saying "fill this in or else!"

Field(...) = required, no default
⚙️

Field() — Description + Constraints

We've seen Field() before. New here: it's used on every field including required ones. The description= text ends up in the JSON Schema — so the LLM sees it when you use output_type=. Good descriptions = better LLM extractions.

description goes into JSON Schema
🏷️

Annotated — The Modern Way (v2)

Annotated[str, Field(...)] moves the Field() call into the type annotation. The type and its metadata are bundled together. This is the Pydantic v2-recommended pattern. Tools like mypy and IDEs understand it better, and it avoids a known ambiguity with None defaults.

type + metadata = one unit
🔀

int | None — Union Type (Python 3.10+)

The pipe | operator creates a union type: "this can be an int, OR None". The modern replacement for Optional[int] from the typing module. Cleaner, shorter, no import needed. int | None and Optional[int] are 100% equivalent.

Python 3.10+ — no typing import!
📋

list[str] — Python 3.9+ Lowercase

Both files use list[str] with lowercase l. This works in Python 3.9+. Before 3.9, you had to write List[str] (uppercase, imported from typing). These two files don't import List from typing — proof they target Python 3.9+.

Python 3.9+ — built-in generics
🧪

Test-Driven Structure

Both files use try/except ValidationError as a self-contained test suite. First test: valid data → should print nothing (or the object). Second test: invalid rating (6) → should print the error. This pattern is common for quickly demonstrating validation behaviour.

test valid then invalid
💡 The One Big Difference Between v1 and v2

Both files define identical validation rules and produce identical results. The only difference is syntax style:

v1 style: field: type = Field(default_or_..., constraint=...) — Field as the default value.
v2 style: field: Annotated[type, Field(constraint=...)] = default — Field in the annotation, default separately.

The v2 style is Pydantic's official recommendation because it's unambiguous: the type and its constraints are bundled together, and the default value is clearly separate (after =).

Section 03

The ... Ellipsis — "This Field Is Required"

Python's built-in Ellipsis object used as a mandatory field marker in Pydantic v1 style.

… Required (Field(...))
name: str = Field(..., description="Product name")
... is the Ellipsis — a Python singleton (like True or None but less famous). Pydantic interprets it as "no default — user must supply this".

Missing it: Product(price=999) → ValidationError: name field required.
None = Optional default
rating: int = Field(None, description="Rating...")
None as first arg means "default value is None". So if you don't provide rating, Pydantic stores None automatically. This is the v1 way to make a field optional.

In v2 style: Annotated[int | None, Field(...)] = None — cleaner.
🔍 What Exactly IS ...?

... is Python's Ellipsis literal. It evaluates to the singleton object Ellipsis. You can type it in the REPL: type(...) → <class 'ellipsis'>. It was originally for slicing multidimensional arrays in NumPy. Pydantic hijacked it as a "required" marker because it's a unique object that can't be confused with a real default value. In v2 syntax, you don't need it at all — a field without = default is automatically required.

v1 Syntaxv2 SyntaxMeaning
name: str = Field(...) name: Annotated[str, Field()] Required — must be provided
rating: int = Field(None) rating: Annotated[int | None, Field()] = None Optional — defaults to None
score: int = Field(5) score: Annotated[int, Field()] = 5 Optional — defaults to 5
In v2, a field with no = default is automatically required — no need for ...
Section 04

int | None — The Modern Union Type

Python 3.10 introduced | for union types. v2 uses it instead of Optional[int].

Old way (pre-3.10)
from typing import Optional
rating: Optional[int] = None
Needs an import from typing. Works back to Python 3.5+. Still valid today.
=
New way (Python 3.10+)
# no import needed
rating: int | None = None
No import. Cleaner. Reads like English: "int or None". Python 3.10+ required.
🔍 What Does int | None Actually Mean for Validation?

int | None means Pydantic will accept either an integer value or the value None.

rating=5 → ✅ integer, valid
rating=None → ✅ None, valid (field is omitted or explicitly set to None)
rating="high" → ✗ ValidationError (not an int or None)

Combined with ge=1, le=5: if a value IS provided (not None), it must be between 1 and 5. If it's None, the ge/le constraints don't apply.

🧪 Why Both Files Print the Same Thing

The two syntax styles — Field(None, ge=1, le=5) vs Annotated[int | None, Field(ge=1, le=5)] = None — are semantically identical. Pydantic generates the same internal validation logic from both. The difference is purely about code clarity and tooling support, not runtime behaviour. The JSON Schema produced by model_json_schema() is also identical.

Section 06

Commented Code — Both Files

Every field, every syntax choice, every test explained.

product_v1.py CLASSIC FIELD() STYLE 
from pydantic import BaseModel, Field, ValidationError
# Field      → add descriptions and constraints to any field
# ValidationError → the exception Pydantic raises when validation fails
# No 'Optional' or 'List' imports — using Python 3.9+ built-in generics!

class Product(BaseModel):

    name: str = Field(..., description="Product name")
        # str = type. Field(...) = required, no default.
    # '...' (Ellipsis) is Python's way of saying "mandatory — fill this in".
    # description= ends up in model_json_schema() → LLMs read this!

    price: float = Field(..., description="Price of the product")
        # float required. No min/max constraint — any price (even negative?) is accepted.
    # In production: add ge=0.0 to prevent negative prices.

    quantity: int = Field(..., description="Available stock quantity")
        # int required. Again, no ge=0 — negative stock would be accepted!
    # These descriptions let the LLM know these are required fields.

    rating: int = Field(None, description="User rating between 1-5 stars", ge=1, le=5)
        # THE TRICKY ONE. Breaking it down:
    #   rating: int     → the type hint says int
    #   Field(None,...) → first arg is the DEFAULT VALUE (None)
    #                     so if not provided, rating = None
    #   ge=1            → if a value IS provided, it must be ≥ 1
    #   le=5            → if a value IS provided, it must be ≤ 5
    #
    # PROBLEM: the type says 'int' but the default is None (not an int!).
    # Pydantic v2 allows this but it's technically inconsistent — the type
    # should be 'int | None' or 'Optional[int]'. This is the v1 ambiguity.
    # rating=None → OK (default)
    # rating=3    → OK (1 ≤ 3 ≤ 5)
    # rating=6    → ValidationError (6 > 5, violates le=5)

    features: list[str] = Field(..., description="Key product features")
        # list[str] — Python 3.9+ lowercase list with generic parameter.
    # Required (... ellipsis). Each item must be a string.
    # Pass: ["SSD", "16GB RAM"] → ✅
    # Pass: [1, 2, 3]          → coerced to ["1", "2", "3"] (Pydantic coerces)


# ─── TEST SUITE ─────────────────────────────────────────────────────────────
print("--- Testing Valid Data ---")
try:
    p1 = Product(name="Laptop", price=999.99, quantity=10, rating=5, features=["SSD", "16GB RAM"])
        # All fields valid:
    # name="Laptop"       → str ✅
    # price=999.99        → float ✅
    # quantity=10         → int ✅
    # rating=5            → int, 1 ≤ 5 ≤ 5 ✅
    # features=[...]      → list[str] ✅
    # p1 is created — no exception. Nothing prints from the except block.
except ValidationError as e:
    print(e)

print("\n--- Testing Invalid Rating (6) ---")
try:
    Product(name="Phone", price=500.0, quantity=5, rating=6, features=["5G"])
        # rating=6 violates le=5 constraint.
    # Pydantic raises ValidationError immediately on construction.
    # The Product object is NEVER created — the except block fires.
except ValidationError as e:
    print(e)
        # Prints: "1 validation error for Product / rating / Input should be ≤ 5"
product_v2.py MODERN ANNOTATED STYLE 
from typing import Annotated
# ONLY Annotated is imported from typing.
# No Optional, no List — modern Python handles these natively.
# Annotated = a typing wrapper that attaches metadata to a type.
# Annotated[str, Field(...)] = "str, and here's extra info about it"

from pydantic import BaseModel, Field, ValidationError


class Product(BaseModel):

    name: Annotated[str, Field(description="Product name")]
        # Annotated[str, Field(...)] bundles the type (str) with its metadata (Field).
    # No '...' needed — a field with no '= default' is automatically required in v2.
    # No default after the annotation → required.
    # Equivalent to v1's: name: str = Field(..., description="...")

    price: Annotated[float, Field(description="Price of the product")]
    quantity: Annotated[int, Field(description="Available stock quantity")]

    rating: Annotated[int | None, Field(description="User rating between 1-5 stars", ge=1, le=5)] = None
        # SAME AS V1 RATING — but now crystal clear. Reading it left to right:
    #
    # Annotated[         → "I'm attaching metadata to a type"
    #   int | None,      → the type: integer OR None (Python 3.10+ union syntax)
    #   Field(           → here's the metadata:
    #     description=,  → text for JSON Schema / LLM
    #     ge=1, le=5     → if a value is given, it must be 1–5
    #   )
    # ] = None           → the DEFAULT VALUE is None (field is optional)
    #
    # Compare to v1: rating: int = Field(None, description=..., ge=1, le=5)
    # In v1: where is the default? Mixed INTO Field()'s first arg — confusing.
    # In v2: the default is clearly AFTER = — unambiguous!
    #
    # int | None makes it honest: "this is an int OR None"
    # Without | None, type would claim it's always int but default is None — lie!

    features: Annotated[list[str], Field(description="Key product features")]
        # Required list[str]. Same as v1. No default → must be provided.


# ─── IDENTICAL TEST SUITE ───────────────────────────────────────────────────
print("--- Testing Valid Data ---")
try:
    p1 = Product(name="Laptop", price=999.99, quantity=10, rating=5, features=["SSD", "16GB RAM"])
        # Same valid data as v1 → same success, no exception.
except ValidationError as e:
    print(e)

print("\n--- Testing Invalid Rating (6) ---")
try:
    Product(name="Phone", price=500.0, quantity=5, rating=6, features=["5G"])
        # rating=6 still violates le=5 → same ValidationError as v1.
    # Proof: the underlying validation rules are identical in both styles.
except ValidationError as e:
    print(e)

🚀 The Full Picture — How This Connects Forward

The description= field in every Field() call isn't decoration — it's LLM communication. When you use Agent(output_type=Product):

Product.model_json_schema() generates a schema where each field has a "description" key pulled directly from Field(description=...). The LLM reads these descriptions to understand what to extract or generate for each field.

Better descriptions = better LLM output. description="Price of the product in USD, positive number" beats description="Price" every time. That's why these two files write descriptions on every field — and why the v2 style that makes the code cleaner also makes it easier to maintain good descriptions.
