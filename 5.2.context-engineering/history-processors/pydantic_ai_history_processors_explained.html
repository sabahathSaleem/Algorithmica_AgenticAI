History Processors Explained

How AI agents remember conversations — and how we control what they remember — using smart history filters & summarizers.

🤖 💬 🧠 ✂️ 📝 🔢
01

🌍 Big Picture — What & Why?

🤖

What is an AI Agent?

An AI agent is a program that uses an LLM (like GPT or LLaMA) to think, respond, and use tools. It's not just a chatbot — it can take actions.

It's like a super-smart robot assistant who can answer questions AND do things like search the web or write files.
💬

What is Message History?

Every time you chat with an AI, it keeps a log of all past messages — both what YOU said (requests) and what the AI replied (responses). This is sent back with every new question so the AI remembers context.

It's like showing the AI a copy of your entire WhatsApp chat before asking it a new question every single time.
🚨

The Problem — Context Windows

AI models can only read a limited amount of text at once (called a context window). Long conversations use too many tokens (word-pieces), making the AI slow and expensive — or crashing it.

Imagine if you could only remember the last 10 pages of a book. If the book gets too long, you have to forget some pages!
✂️

History Processors = The Solution

A history_processor is a function you plug into an agent. Before each new call, it trims, filters, or summarizes the history so only the most useful messages are sent to the AI.

It's like a librarian who removes old, unneeded pages from the book before you read it — keeping just the good bits!
🪙

What are Tokens?

Tokens are small pieces of text — roughly ¾ of a word. AI models charge by token and have limits on how many they can process. Tracking tokens helps us know when to trim the history.

If words are Lego bricks, tokens are the individual bumps on each brick. The more text, the more bumps — and there's a limit to how many fit in the box!
📊 How History Processors Fit In
User sends new message
→
history_processor runs
→
Filtered/trimmed history
→
Sent to AI model
→
AI responds
Without processor: ALL past messages sent (slow & expensive)
→
With processor: only what matters sent (fast & cheap!)
🐍

What is PydanticAI?

PydanticAI is a Python framework for building AI agents. It uses Pydantic (a data-validation library) to define structured inputs/outputs for agents. The Agent class wraps an LLM and lets you attach tools, instructions, and history processors.

🧩

What is RunContext (Deps)?

Some history processor functions accept a RunContext object as their first argument. This lets you pass extra data (like token counts, limits, config) into the processor at runtime — via a @dataclass called Deps. Think of it as passing a settings bag to the function.

📁 File A — Request / Response Filter

a_req_res_only_filter.py Filter by Message Type Simplest filter — no Deps needed

🎯 What this file does

It shows 3 different filter strategies: (1) keep only user messages, (2) keep only AI replies, (3) keep only AI replies from history BUT always include the latest user message. Strategy 3 is the one actually plugged into the agent.

ModelRequest = user messages ModelResponse = AI messages isinstance() = check the type No RunContext needed
a_req_res_only_filter.py — fully annotated
# ── IMPORTS ─────────────────────────────────────────────────────────────────
from pydantic_ai import Agent, ModelMessage, ModelMessagesTypeAdapter,
                          ModelRequest, ModelResponse
# ModelRequest  → a message that came FROM the user (your question)
# ModelResponse → a message that came FROM the AI (its answer)
# ModelMessage  → parent type — can be either of the above

# ── FILTER 1: Keep ONLY user messages ────────────────────────────────────────
def request_only_filter(messages: list[ModelMessage]) -> list[ModelMessage]:
    # For each message in history, keep it ONLY if it's a user message (ModelRequest)
    # Result: AI never sees its own previous answers — only what users said
    return [msg for msg in messages if isinstance(msg, ModelRequest)]
    ⚠️ Rarely useful alone — AI loses all memory of what it said

# ── FILTER 2: Keep ONLY AI responses — but BROKEN ────────────────────────────
def response_only_filter1(messages: list[ModelMessage]) -> list[ModelMessage]:
    # Keep only AI messages — BUT this removes the current user question too!
    # The AI won't know what the user just asked ← BAD pattern
    return [msg for msg in messages if isinstance(msg, ModelResponse)]
    ❌ Bug: loses the latest user question!

# ── FILTER 3: Keep AI responses + always include latest user message ──────────
def response_only_filter2(messages: list[ModelMessage]) -> list[ModelMessage]:
    # messages[-1] is always the CURRENT user message (most recent)
    # messages[:-1] is all the OLDER history (everything except latest)
    
    # Step 1: From old history, pick only AI responses
    temp = [msg for msg in messages[:-1] if isinstance(msg, ModelResponse)]
    
    # Step 2: Always add back the latest user message at the end
    temp.append(messages[-1])
    
    # Result: AI sees its past answers + the current question (ignores old user msgs)
    return temp
    ✅ The one actually used — smart & correct!

# ── AGENT SETUP ──────────────────────────────────────────────────────────────
agent = Agent(
    'ollama:llama3-groq-tool-use:8b',          # Which AI model to use (local LLaMA)
    instructions="You are helpful assistant.",   # System prompt for the AI
    history_processors=[response_only_filter2]   # Plug in our filter here!
)                                                  📌 This is where magic happens

# ── LOAD HISTORY FROM FILE ────────────────────────────────────────────────────
history = ModelMessagesTypeAdapter.validate_python(history)
# history.json stores past conversations saved from a previous run
# validate_python() converts raw JSON dicts → proper ModelMessage objects

# ── RUN THE AGENT ─────────────────────────────────────────────────────────────
result = agent.run_sync(
    "Tell me a different motto compared to past.", # New user question
    message_history=history                         # Pass the loaded history
)
# Before calling the AI, response_only_filter2() runs on 'history'
# → trims it → filtered version sent to AI model

print(result.output)   # What the AI said
print(result.usage())  # How many tokens were used
💡

Key Insight: messages[-1] is always the current user message

PydanticAI always appends the new user message at the end of the list before passing it to the history processor. So messages[-1] is ALWAYS the new question. messages[:-1] is all past history.

📁 File B — Most Recent N Messages Filter

b_most_recent_only_filter.py Sliding Window Filter Uses Deps (RunContext) to pass config

🎯 What this file does

Keeps only the most recent N messages from history. N is passed in at runtime via a Deps dataclass. Great for keeping recent context without token bloat.

RunContext carries runtime config @dataclass for structured Deps messages[-N:] = last N items Sliding window pattern
b_most_recent_only_filter.py — fully annotated
from dataclasses import dataclass        # For creating simple data containers
from pydantic_ai import Agent, ModelMessage, RunContext

# ── THE FILTER ────────────────────────────────────────────────────────────────
def most_recent_only_filter(
    ctx: RunContext[Deps],     # RunContext lets us read settings (Deps)
    messages: list[ModelMessage]
) -> list[ModelMessage]:
    
    # ctx.deps is our Deps object containing num_messages_to_keep
    n = ctx.deps.num_messages_to_keep
    
    # Python slice trick: list[-n:] gives you the LAST n items
    # e.g. [a, b, c, d, e][-3:]  →  [c, d, e]
    return messages[-n:]
    🪟 Sliding window — only recent context

# ── AGENT ─────────────────────────────────────────────────────────────────────
agent = Agent(
    'ollama:llama3-groq-tool-use:8b',
    instructions="You are helpful assistant.",
    history_processors=[most_recent_only_filter]
    # Note: this processor takes RunContext — PydanticAI detects this automatically
)

# ── DEPS DATACLASS ────────────────────────────────────────────────────────────
@dataclass
class Deps:
    num_messages_to_keep: int   # How many recent messages to keep

# Create a Deps object — we want to keep the last 3 messages
deps = Deps(num_messages_to_keep=3)
3 = only last 3 messages sent to AI

# ── RUN ───────────────────────────────────────────────────────────────────────
result = agent.run_sync(
    "Tell me a different motto compared to past.",
    message_history=history,
    deps=deps           # Pass our settings to the processor via RunContext
)
🎒

RunContext[Deps] — The Settings Backpack

Think of RunContext[Deps] as a backpack that carries your settings into the function. You pack the backpack with Deps(num_messages_to_keep=3) when calling run_sync(deps=deps), and the function unpacks it with ctx.deps.num_messages_to_keep.

📁 File C — Token Count Based Filter

c_token_count_based_filter.py Smart Token-Budget Trimmer Only trims when token limit is hit

🎯 What this file does

Tracks the running token count across calls. Only trims history when the total tokens exceed a limit. This simulates a real production use-case where you budget API costs carefully.

Stateful token tracking Conditional trimming result.usage() = token count Multi-turn simulation
c_token_count_based_filter.py — fully annotated
from dataclasses import dataclass
from pydantic_ai import Agent, ModelMessage, RunContext

# ── THE FILTER ────────────────────────────────────────────────────────────────
def token_usage_based_filter(
    ctx: RunContext[Deps],
    messages: list[ModelMessage]
) -> list[ModelMessage]:

    current_tokens   = ctx.deps.total_tokens       # Tokens used so far
    token_limit      = ctx.deps.token_limit         # Our budget ceiling
    n                = ctx.deps.num_messages_to_keep

    # Only trim if we've EXCEEDED the token budget
    if current_tokens > token_limit:
        return messages[-n:]    # Keep only the last N messages
        ✂️ Trim triggered!

    return messages              # Under budget? Send everything as-is
    ✅ No trimming needed yet

# ── DEPS: carries 3 pieces of info ────────────────────────────────────────────
@dataclass
class Deps:
    total_tokens: int           # How many tokens we've spent so far
    token_limit: int            # Our max budget (e.g. 100 tokens)
    num_messages_to_keep: int   # How many to keep if we need to trim

# ── FIRST CALL: starting fresh, 0 tokens used ────────────────────────────────
ntokens = 0
deps = Deps(token_limit=100, total_tokens=ntokens, num_messages_to_keep=3)
result = agent.run_sync("Tell me a different motto compared to past.",
                        message_history=history, deps=deps)
print(result.output)
print(result.usage())   # Shows: input_tokens, output_tokens, total_tokens

# ── UPDATE TOKEN COUNT ────────────────────────────────────────────────────────
ntokens += result.usage().input_tokens + result.usage().output_tokens
# Add up all tokens from this call → total spent so far
📊 Running total now updated

# ── SECOND CALL: token count now likely OVER 100 ──────────────────────────────
deps = Deps(token_limit=100, total_tokens=ntokens, num_messages_to_keep=3)
result = agent.run_sync("Tell me a different motto compared to past.",
                        message_history=history, deps=deps)
# This time, token_usage_based_filter sees total_tokens > 100
# → It will trim history to the last 3 messages before calling AI
print(result.output)
print(result.usage())
⚠️

Important: history is not updated between calls

Notice that history is passed as-is to both run_sync calls — it's the same loaded file. In a real app, you'd append new messages to history after each call. This demo just shows the token-triggered trimming logic.

📁 File D — Token Count Based Summarizer

d_token_count_based_summarizer.py Compress, Don't Forget! Uses a second agent to summarize old messages

🎯 What this file does

Instead of simply deleting old messages when the token limit is hit, this uses a second summarization agent to compress the old messages into a short summary — then uses that summary + the current message as history. Best of both worlds: small context AND no lost information!

Agent-within-an-Agent pattern Summarization vs deletion new_messages() extraction Most advanced strategy
d_token_count_based_summarizer.py — fully annotated
from dataclasses import dataclass
from pydantic_ai import Agent, ModelMessage, RunContext

# ── A SEPARATE AGENT JUST FOR SUMMARIZING ─────────────────────────────────────
summarize_agent = Agent(
    'ollama:llama3-groq-tool-use:8b',
    instructions="Summarize this conversation, omitting small talk and unrelated topics."
)
# This is NOT the main agent — it's a helper agent whose only job is
# to take a list of messages and return a condensed summary
🤖 Agent #2: the summarizer assistant

# ── THE PROCESSOR ─────────────────────────────────────────────────────────────
def token_based_summarizer(
    ctx: RunContext[Deps],
    messages: list[ModelMessage]
) -> list[ModelMessage]:

    print(ctx.deps.total_tokens)   # Debug: see how many tokens we've used

    if ctx.deps.total_tokens > ctx.deps.token_limit:
        # We're over budget!

        # Take all messages EXCEPT the latest one (that's the current user question)
        oldest_messages = messages[:-1]
        📜 All old context to be compressed

        # Run the SUMMARIZER AGENT on the old messages
        summary = summarize_agent.run_sync(message_history=oldest_messages)
        # This calls the AI again — but with a "summarize this" system prompt
        # The result is a short paragraph summarizing the whole past conversation
        🔁 AI call inside AI call!

        # summary.new_messages() extracts just the summary output as a message list
        # Then append the current user question (messages[-1])
        return summary.new_messages() + messages[-1:]
        # Result: [short_summary_message, current_user_question]
        ✅ Compact but info preserved

    return messages   # Under budget? Send full history unchanged

# ── MAIN AGENT (uses the summarizer processor) ────────────────────────────────
agent = Agent(
    'ollama:llama3-groq-tool-use:8b',
    instructions="You are helpful assistant.",
    history_processors=[token_based_summarizer]
)

# ── DEPS ──────────────────────────────────────────────────────────────────────
@dataclass
class Deps:
    total_tokens: int    # Running token total
    token_limit: int     # When to trigger summarization (e.g. 100)

# ── CALL 1: Under limit — full history sent ───────────────────────────────────
ntokens = 0
deps = Deps(token_limit=100, total_tokens=ntokens)
result = agent.run_sync("Tell me a different motto compared to past.",
                        message_history=history, deps=deps)
print(result.output)
print(result.usage())

# ── UPDATE TOKEN COUNT ────────────────────────────────────────────────────────
ntokens += result.usage().input_tokens + result.usage().output_tokens

# ── CALL 2: Likely over limit — summarizer kicks in ──────────────────────────
deps = Deps(token_limit=100, total_tokens=ntokens)
result = agent.run_sync("Tell me a different motto compared to past.",
                        message_history=history, deps=deps)
# Now: old history → summarized → summary + current question → sent to AI
✨

Agent-in-Agent Pattern

This is an advanced agentic pattern: a meta-agent that spawns a sub-agent to do a specific task (summarizing) and uses its output as part of the main flow. This is how real production AI pipelines work — orchestrators that call specialists!

🏆 Which Strategy Should You Use?

✂️

Request/Response Filter

Good for debugging or when you only want to show the AI its own outputs. Rarely used in production on its own.

🪟

Most Recent N Filter

Good for short-term context tasks — like a support chatbot that only needs the last few exchanges. Simple and fast.

💰

Token-Based Trim

Good for cost-controlled apps. Only trims when you actually need to — so context is preserved until the budget is hit.

🧠

Token-Based Summarize

Best for production. Compresses old context instead of deleting it. The AI retains knowledge without blowing up the token budget.

What is Logfire?

Every file imports logfire and calls logfire.configure() + logfire.instrument_pydantic_ai(). Logfire is an observability tool — it records every agent call, token usage, and history trace so you can see exactly what's happening in your AI app. Think of it as console.log() on steroids for AI agents.
