Before the Code
New Concepts to Understand First
These two files introduce 3 powerful new ideas on top of what you learned before. Let's make them crystal clear.
🏷️
@dataclass
A Python shortcut to create a simple data-holding class. Instead of writing __init__ yourself, just annotate with @dataclass and Python auto-creates it. Like a labelled box for storing related values.
🎛️
deps= (Dependencies)
When you call agent.run_sync(..., deps=user), you're injecting extra data into the agent run. The agent can then access that data inside its instructions. Like slipping a sticky note to the AI before it starts.
🧵
RunContext[T]
A special object PydanticAI gives you inside dynamic instruction functions. It holds everything about the current run — deps, model, usage, run ID. The [T] means the type of your deps object.
🎨
@agent.instructions decorator
Instead of a fixed instructions string, you write a function that builds the instructions at runtime. This lets you personalize, localize, or inject user data into every single prompt dynamically.
🔄
Static vs Dynamic Instructions
Static: same instructions every run. Dynamic: instructions built fresh each run using the current user's data. Dynamic = personalization at scale.
🔬
Observability via ctx
The RunContext exposes internal state: which model is running, how many tokens used so far, run ID, step number. Great for debugging, logging, or building adaptive AI systems.
🍕
The Pizza Analogy for deps + RunContext: A pizza shop (Agent) has a standard recipe (static instructions). But each customer (deps) has preferences — John wants extra cheese, Ram wants spicy. The chef reads the order ticket (RunContext) to personalize the pizza (dynamic instructions) before baking. Same shop, same oven, but a custom pizza for every customer.

File A
Dynamic Personalized Prompts
Same agent, two different users — two different personalized responses. The instructions change on-the-fly based on who's calling.
🎭
Think of it like a TV news anchor reading a teleprompter. The format is always the same, but the name of who they're addressing changes every broadcast. The @agent.instructions function is the person updating that teleprompter right before the camera goes live.
a_dynamic_prompt.py
Intermediate
What it does: Creates a UserProfile dataclass. A dynamic instruction function reads the user's name from deps and injects it into the prompt. Runs twice — once for "john", once for "ram" — proving the instructions are truly dynamic.
⚠️
Heads up — there's a bug in this file! UserProfile is used before it's defined (line 17 references it, but it's defined on line 22). In Python, this causes a NameError. Fix: move the @dataclass block above the agent = Agent(...) line. This is a common mistake when writing quickly!
python
1from dataclasses import dataclass # lets us create simple data holder classes
2from dotenv import load_dotenv
3from pydantic_ai import Agent, RunContext # RunContext = the "live info" object during a run
4import logfire
5
6load_dotenv(override=True)
7logfire.configure()
8logfire.instrument_pydantic_ai()
9
10# 🤖 Agent with a boring, fixed base instruction
11agent = Agent(
12 'ollama:llama3-groq-tool-use:8b',
13 instructions="You are a helpful assistant.", # static fallback instruction
14)
15
16# ✨ THE MAGIC — @agent.instructions turns a function into a prompt builder!
17# This function runs BEFORE every agent call to dynamically build instructions
18@agent.instructions # 👈 decorator: "hey agent, use this function to build instructions"
19def personalized_prompt(ctx: RunContext[UserProfile]):
20 # ctx = RunContext, typed with UserProfile so Python knows what ctx.deps looks like
21 username = ctx.deps.name # 🔍 dig into the injected deps to get the name
22 return f"Always include following username in the response. {username}"
23 # ☝️ returns a STRING — this gets ADDED to the system prompt before the LLM sees it
24
25# 📦 Simple data class — holds user info. @dataclass auto-creates __init__
26@dataclass
27class UserProfile:
28 name: str # just one field for now — user's name
29
30# 👤 Run 1: user is "john"
31user = UserProfile(name="john")
32response = agent.run_sync("Tell me a joke in short", deps=user)
33# ☝️ deps=user — this is how UserProfile data enters the RunContext
34print(response.output) # AI will address "john" in the joke
35print(response.usage())
36
37# 👤 Run 2: SAME agent, SAME prompt, but different user — "ram"
38user = UserProfile(name="ram")
39response = agent.run_sync("Tell me a joke in short", deps=user)
40print(response.output) # AI will address "ram" — completely different personalization!
41print(response.usage())
🔑
The @agent.instructions decorator is the hero. It takes a plain function and promotes it to a "prompt builder" — run before every call. The function receives ctx (the RunContext), which holds deps — your injected user data.
📐
Why RunContext[UserProfile] with the type in brackets? This is called a Generic type. It tells Python (and your IDE): "ctx.deps will be of type UserProfile". Without it, Python doesn't know what fields ctx.deps has, and you lose autocomplete + type safety.
➕
Static + Dynamic instructions stack! The base instructions="You are a helpful assistant." is always there. The returned string from the function is appended to it. So the AI gets both.

b_run_info.py
Intermediate+
What it does: Identical structure to File A, but the instruction function now prints all available RunContext fields before returning the instructions string. It also runs the same agent twice to show how run_id and run_step differ between runs.
python
1from dataclasses import dataclass
2from dotenv import load_dotenv
3from pydantic_ai import Agent, RunContext
4import logfire
5
6load_dotenv(override=True)
7logfire.configure()
8logfire.instrument_pydantic_ai()
9
10agent = Agent(
11 'ollama:llama3-groq-tool-use:8b',
12 instructions="You are a helpful assistant.",
13)
14
15@agent.instructions
16def dynamic_instructions(ctx: RunContext[UserProfile]):
17 print("#### Information available in Runtime context")
18
19 print(ctx.usage) # 📊 token usage so far in this run (input + output tokens)
20 print(ctx.deps) # 📦 the UserProfile object you passed in via deps=
21 print(ctx.model) # 🤖 which model is being used (e.g. ollama/llama3...)
22 print(ctx.prompt) # 💬 the user's actual message ("Tell me a joke in short")
23 print(ctx.run_id) # 🔑 unique ID for this run — changes every time run_sync() is called
24 print(ctx.run_step) # 🪜 which step in the run this is (useful for multi-step agents)
25
26 username = ctx.deps.name # extract the name from deps as before
27 return f"Always include following username in the response. {username}"
28
29@dataclass
30class UserProfile:
31 name: str
32
33deps = UserProfile(name="john") # 👤 create user object
34
35# 🚀 Run 1 — note the run_id that prints inside the function
36response = agent.run_sync("Tell me a joke in short", deps=deps)
37print(response.output)
38print(response.usage())
39
40# 🚀 Run 2 — SAME deps, SAME prompt, but run_id will be DIFFERENT
41# This proves each run_sync() call is a fresh independent run
42response = agent.run_sync("Tell me a joke in short", deps=deps)
43print(response.output)
44print(response.usage())
🔑
Why run it twice with the same deps? To prove run_id is unique per call. Each run_sync() generates a fresh UUID. This matters for logging, tracing, and debugging in production systems.
🪜
What is run_step? Some agents do multiple LLM calls in one run (e.g. tool use → reflect → answer = 3 steps). run_step tells you which step we're on. For simple single-turn calls, it'll just be 0 or 1.
Deep Dive
RunContext — Every Field Explained
Your cheat sheet for everything you can access inside a @agent.instructions function via ctx.
What you can access inside ctx
Field Type What it gives you
📦 ctx.deps T (your type) The object you passed in via deps= when calling run_sync(). Access your user data here.
🤖 ctx.model Model Which LLM is running. Useful if you want to conditionally adjust prompts based on model capability.
💬 ctx.prompt str | list The user's actual input message sent to the agent. Great for logging or conditional instruction logic.
📊 ctx.usage Usage Token counts so far — input tokens, output tokens, total. Use this to track costs or enforce limits.
🔑 ctx.run_id str (UUID) Unique ID generated fresh every run_sync() call. Perfect for logging, tracing, and correlating events.
🪜 ctx.run_step int Which step in a multi-step run we're on. Starts at 0. For tool-use agents that loop, this increments each cycle.
@dataclass
Auto-generates __init__, __repr__. Less boilerplate than a regular class.
deps=
Keyword arg in run_sync(). Whatever you pass here lands in ctx.deps.
RunContext[T]
Generic class. The [T] tells the type checker what shape ctx.deps has.
@agent.instructions
Decorator that registers a function as a dynamic prompt builder. Called before every LLM request.
ctx.run_id
New UUID each call. Same agent + same user = different IDs. Enables distributed tracing.
ctx.usage
Token usage object. Critical for cost monitoring in production.
