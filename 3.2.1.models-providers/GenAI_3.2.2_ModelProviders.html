Section 01

Core Concepts

New ideas introduced in these two files that go beyond the Week 1 basics.

🏷️

Model by Name (String)

Pass a 'provider:model' string to Agent(). pydantic_ai resolves everything automatically: finds the right class, reads API keys from environment, creates an HTTP client. Fast and clean for development.

zero config, great for prototyping
🏗️

Model by Object (Instance)

Explicitly construct a GroqModel(...) or OpenAIChatModel(...) instance and pass it to Agent(). You control every detail: custom provider, API key source, HTTP config, timeout. Use this in production.

full control, production-ready
🔌

Provider Object

A Provider (e.g. GroqProvider, OllamaProvider) is a separate object that handles how to connect to the backend — API key, base URL, HTTP client. Models and providers are decoupled so you can mix and match.

auth + transport layer
⚙️

AsyncClient (Custom HTTP)

The Groq SDK's AsyncClient lets you customise the HTTP connection: set timeouts, retry logic, proxies, or connection pooling. Pass it into a provider to override the default HTTP behaviour.

timeout / proxy / retry control
🤗

HuggingFace + Novita

HuggingFaceModel + HuggingFaceProvider lets you call any model on HuggingFace Inference API. The provider_name='novita' parameter routes through Novita, a cloud that hosts HF models cheaply.

HF_TOKEN required
🦙

OpenAIChatModel + OllamaProvider

Ollama exposes an OpenAI-compatible REST API at /v1. So you use OpenAIChatModel (not an Ollama-specific class) and point it at localhost with OllamaProvider. This pattern works for any OpenAI-compatible local server.

OpenAI-compatible API trick
💡 The Big Idea Across Both Files

by-name.py is what you write on Day 1. by-object.py is what your code evolves into when you need production reliability — custom timeouts so your app doesn't hang, explicit key injection for security, or switching providers without changing environment variables. Same Agent, same output, completely different level of control.

The same Groq LLaMA 3.3 70B call, two completely different approaches.

Section 03

Providers Deep Dive

Four different backends used (or prepared) in by-object.py, each with a distinct purpose.

GroqModel (simple) active
GroqModel('llama-3.3-70b-versatile')

The simplest by-object form. No provider argument — pydantic_ai auto-creates a GroqProvider using GROQ_API_KEY from env. One step above by-name: you get a typed object, but still no manual config.

ACTIVE IN CODE AUTO-PROVIDER
GroqModel + GroqProvider # commented
GroqProvider(api_key=os.getenv('GROQ_API_KEY'))

Explicitly passes the API key into the provider. Useful when key comes from a vault, a database, or a per-user dynamic source — not just a static env var. Makes the auth flow auditable and testable.

COMMENTED OUT EXPLICIT KEY
GroqProvider + AsyncClient # commented
AsyncClient(timeout=30)

The most powerful Groq config. AsyncClient is Groq's own async HTTP client. timeout=30 means: if the LLM doesn't respond within 30 seconds, raise a timeout exception. Critical for production APIs where hanging is worse than failing.

COMMENTED OUT TIMEOUT CONTROL
HuggingFaceModel + Novita # commented
HuggingFaceModel('Qwen/Qwen3.5-35B-A3B')

Calls a HuggingFace model (Qwen3.5 35B MoE) via Novita — a cheap GPU cloud that hosts HF models with an API. provider_name='novita' tells HuggingFaceProvider to route to Novita's endpoint instead of HF's own servers.

COMMENTED OUT HF_TOKEN NOVITA CLOUD
OpenAIChatModel + OllamaProvider # commented
OllamaProvider(base_url='http://localhost:11434/v1')

The clever one. Ollama mimics OpenAI's API format at /v1. So you use OpenAIChatModel (not a dedicated Ollama class) and override the base URL. This pattern works with any local server that speaks the OpenAI API spec (LM Studio, llama.cpp, vLLM, etc.).

COMMENTED OUT LOCAL OPENAI-COMPAT
🔑 The OpenAI-Compatible API Pattern

This is huge in the local LLM ecosystem. OpenAI's API format (POST to /v1/chat/completions with messages array) has become the industry standard. Ollama, LM Studio, llama.cpp, vLLM, and many others implement it. That means pydantic_ai's OpenAIChatModel works with ALL of them — just swap the base_url. No custom code needed per platform.

Section 04

Understanding the Commented-Out Blocks

The grayed lines in by-object.py aren't dead code — they're a recipe book your mentor left for you.

📖 Why Commented Code Matters Here

In production GenAI codebases, you'll often see commented alternatives next to active code. They show: (1) what the current code replaced, (2) how to escalate if the simple version breaks, and (3) alternative backends you can swap in. Reading these comments teaches you the progression from simple to complex.

Progression: 3 levels of Groq model config

1

Level 1 — Minimal (active)

GroqModel('llama-3.3-70b-versatile') — Name only. pydantic_ai auto-creates a provider using env vars. Use when: prototyping, local dev, you trust env var setup.

2

Level 2 — Explicit Key (commented)

GroqModel('...', provider=GroqProvider(api_key=os.getenv('GROQ_API_KEY'))) — You control where the key comes from. Use when: multi-tenant apps, testing with different keys, reading from secrets manager.

3

Level 3 — Custom HTTP Client (commented)

AsyncClient(timeout=30) injected into GroqProvider. Use when: production APIs where you need timeout guarantees, retry logic, proxy support, or connection pooling. Never leave an LLM call without a timeout in production.

by-name.py MODEL BY STRING 
from dotenv import load_dotenv
from pydantic_ai import Agent
# Minimal imports — only Agent is needed for the by-name approach.
# No model classes, no provider classes. That's the whole point.

load_dotenv(override=True)
# Loads .env file → all API keys (GROQ_API_KEY, OPENAI_API_KEY etc.)
# go into os.environ so pydantic_ai can find them automatically.

agent = Agent(
    #'ollama:llama3-groq-tool-use:8b',       ← local Ollama (commented)
    'groq:llama-3.3-70b-versatile',           # ← currently ACTIVE
        # Format: 'provider_prefix:model_name'
    # pydantic_ai's model resolver reads this string, splits on ':',
    # maps 'groq' → GroqModel class, reads GROQ_API_KEY from env.
    # This is a convenience shortcut — no model object needed.

    #"github:deepseek/DeepSeek-R1",           ← GitHub Models (commented)
    #'openrouter:deepseek/deepseek-v3.2',    ← OpenRouter (commented)
    #'openai:gpt-4o-mini',                   ← OpenAI (commented)
    #'google-gla:gemini-3-pro-preview',      ← Gemini (commented)

        # All these commented lines show you how to SWAP models.
    # To switch: comment the active line, uncomment another.
    # Zero other code changes needed — same by-name pattern.
    # This is the key advantage of the string approach for experimentation.

    instructions="You are a helpful assistant.",
        # System prompt — sent before every user message
)

response = agent.run_sync("Write a haiku about recursion in programming.")
print(response.output)
print(response.usage())

response = agent.run_sync("list top 3 generative models for reasoning")
# New question — open-ended, opinionated answer from the LLM.
# Note: stateless — the LLM does NOT remember the haiku from above.
print(response.output)
print(response.usage())

Section 06

When to Use What

A decision guide and comparison table to know which approach fits your situation.

❓ Which approach should I use?
Need custom timeout / HTTP config?

🏗️ By-Object + Custom AsyncClient

Always set timeouts for production. Use GroqModel + GroqProvider(http_client=AsyncClient(timeout=30))

Just prototyping / exploring?

🏷️ By-Name String

Fastest to write. Agent('groq:llama-3.3-70b-versatile') — done. Swap models by changing one string.

Using HuggingFace or custom backend?

🤗 By-Object only

HuggingFaceModel and exotic providers aren't reachable via the string shortcut. Must use explicit objects.

Local Ollama / vLLM / LM Studio?

🦙 OpenAIChatModel + OllamaProvider

Any OpenAI-compatible local server. OllamaProvider(base_url='http://localhost:11434/v1')

Criteria By-Name (string) By-Object (instance)
Lines of code 1 line 3–7 lines
Imports needed Only Agent Model + Provider + maybe AsyncClient
Custom API key source ✗ Env var only ✓ Any source (vault, DB, etc.)
Timeout control ✗ Default only ✓ Full control via AsyncClient
HuggingFace / exotic backends ✗ Not supported ✓ Via explicit model/provider classes
OpenAI-compatible local servers ⚠ Limited ✓ OpenAIChatModel + custom base_url
Best for Prototyping, scripts, tutorials Production apps, multi-tenant, agentic systems
