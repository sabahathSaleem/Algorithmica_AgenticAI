Tab 01 — Theory

Conceptual Deep Dive

Understand the Agentic AI patterns in this codebase, from the ground up — no prior experience with LLM agents required.

🔍 What Patterns Does This Code Use?
After reverse-engineering all three script families, four core Agentic AI patterns emerge:
  • 1. Tool-Augmented Perception — Sending images (binary data) alongside text prompts so the LLM can "see."
  • 2. Structured Output Enforcement — Forcing the LLM to return a typed schema (Pydantic model), not free-form text.
  • 3. Multi-Agent Pipeline (Classify → Extract) — Two specialized agents working in sequence: one classifies, one extracts.
  • 4. Concurrent Async Orchestration — Running many agent calls simultaneously using Python's async/await + asyncio.gather.
Pattern 1

What Is an LLM "Agent"?

🔑 Key Definition — LLM Agent
An LLM Agent is an AI system that wraps a language model with additional capability: it can receive structured inputs (text + images + tool results), reason about them, and produce structured outputs — all in a loop that can run autonomously. Unlike a plain API call, an agent has a defined role, memory of the conversation, and type-safe output.
🔁 Plain LLM API Call
You send a text string → The LLM responds with a text string. No guarantee on the shape of the response. You manually parse the output. No persistent role.

response = openai.chat.completions.create(...)
text = response.choices[0].message.content
🤖 PydanticAI Agent
You define an agent with an identity (system instructions), an output schema (Pydantic model), and call agent.run(). You get a typed object back — no manual parsing needed.

agent = Agent(model, instructions=..., output_type=Invoice)
result = await agent.run([prompt, image])
💡 Analogy
Think of a plain LLM call as hiring a freelancer with no job description and getting a Word doc in response. A PydanticAI Agent is like hiring a specialist with a clear role, who must deliver a pre-agreed, machine-readable report format — every time.
Pattern 2

Multimodal Inputs — Giving the Agent Eyes

🔑 Key Definition — Multimodal LLM
A Multimodal LLM can process more than one type of input simultaneously. In this codebase, the agent receives both a text instruction and a JPEG image (the PDF page). It reasons across both modalities to extract structure from the document.
🖼️ How BinaryContent Works
PDFs are first rendered to JPEG images (using pdf2image). Each page image is then read as raw bytes and wrapped in a BinaryContent object — which PydanticAI knows how to encode and send to the vision-capable LLM (GPT-4o, Llama 4 Scout).

BinaryContent(data=image_path.read_bytes(), media_type="image/jpeg")

This is then bundled with a text prompt into a single message list that the agent processes together.

Pattern 3

Structured Output — Taming the LLM

🔑 Key Definition — Structured Output
Structured Output forces an LLM to respond in a predefined schema rather than free-form text. PydanticAI uses Pydantic models — Python classes with typed fields — to define this schema. The framework converts the model into a JSON Schema, embeds it in the system prompt, and validates the LLM's response automatically.
📐 The Schema Hierarchy in This Code
  • FileElement → Represents one logical block on a page (table, paragraph, image).
  • ModelAnalysisOutput → The top-level structured response: document type + list of FileElements.
  • OCROutput → The final result object: filename + ModelAnalysisOutput.

Each field has a description that the LLM actually reads to know what to put there. The Field(description=...) annotation is your natural language API contract with the model.
⚠️ Why This Matters
Without structured output, an LLM might say "This looks like an invoice with total $1,200." With it, you get a Python object: invoice.total_amount == 1200.00, invoice.currency == "USD" — directly usable in your downstream code.
Pattern 4

Multi-Agent Pipeline — Specialist Division of Labor

🔑 Key Definition — Multi-Agent System
A Multi-Agent System uses multiple specialized AI agents, each responsible for a distinct subtask, passing outputs from one to the next. This is more reliable than asking one agent to do everything, because each agent can be precisely tuned with its own instructions and output schema.
🔗 The Classifier → Extractor Pipeline (agents_custom.py)
Step 1 — Classifier Agent: Sends the document image and asks "What type of document is this?" Returns a DocumentCategory (invoice, payslip, driver_license).

Step 2 — Extractor Agent: Receives the same image + the category-specific schema (e.g., Invoice). Extracts only the relevant fields for that document type.

This two-step approach is far more accurate than asking one agent to classify AND extract simultaneously — a well-known Agentic AI design principle called separation of concerns.

Pattern 5

Async Concurrency — Parallelizing Agent Calls

🔑 Key Definition — Async/Await in AI Pipelines
Async/Await lets Python run many I/O-bound tasks (like LLM API calls) simultaneously without blocking. Instead of waiting 3 seconds for one document to finish before starting the next, all documents are processed concurrently — reducing total time from N×T to roughly T.
🐌 Sequential (Slow)
Process doc1 → wait 3s → process doc2 → wait 3s → ...
4 documents = 12 seconds
⚡ Concurrent with asyncio.gather
Start all 4 docs simultaneously → all complete in ~3s
4 documents = ~3 seconds
📌 Key Functions in This Codebase
asyncio.gather(*tasks) — fires all coroutines at once, waits for all to finish.
tqdm_asyncio.gather(*tasks) — same, but shows a live progress bar.
asyncio.create_task(...) — schedules a coroutine as a background task immediately.

PydanticAI's agent.run() accepts a list of message parts — not just a string. Mixing text and BinaryContent creates a multimodal prompt. The framework handles encoding the image bytes into the API's expected base64 format behind the scenes. read_bytes() loads the full JPEG into memory as raw bytes.

⚡ Concurrency pattern.Async

The list comprehension builds a list of coroutines (not yet running). *tasks unpacks the list as arguments. tqdm_asyncio.gather launches all coroutines simultaneously, waits for all of them to finish, and returns results in the same order. This is a classic async fan-out pattern.

🧠 Dynamic schema selection — the clever part.Multi-Agent

The extraction agent doesn't have a fixed schema — its output_type is passed in at runtime based on the classifier's output. This means the exact same agent produces an Invoice object for invoices and a DriversLicense object for licenses. It's a pattern called late binding of schemas.

File 3: models/generic.py Pydantic Schema

models/generic.py 
1from pydantic import BaseModel, Field
2from typing import Annotated, List
3
4class FileElement(BaseModel):   # BaseModel = Pydantic's base class for data validation
5    """Represents a single element on a document page."""
6    element_type: Annotated[
7        str,
8        Field(description="Type of the element found on the page", default="")  # LLM reads 'description' as instructions
9    ]
10    element_content: Annotated[
11        str,
12        Field(description="Content of the element found on the page", default="")
13    ]
14
15class ModelAnalysisOutput(BaseModel):   # This is the TOP-LEVEL schema the agent returns
16    """Structured output from the LLM."""
17    file_type: Annotated[str, Field(
18        description="Type name: invoice, internal_document, instruction, other", default=""
19    )]
20    file_elements: Annotated[
21        list[FileElement],          # List of nested objects — LLM must return an array of structured items
22        Field(description="Elements: tables, images, paragraphs, graphs...")
23    ]
24
25class OCROutput(BaseModel):   # Final result combining filename + analysis
26    filename: Annotated[str, Field(default="")]
27    analysis_result: Annotated[ModelAnalysisOutput, Field(default_factory=ModelAnalysisOutput)]
💡 Why Field(description=...) is so important
The description argument inside Field() isn't just documentation for you — PydanticAI converts the entire Pydantic model into a JSON Schema and includes these descriptions as part of the LLM's prompt. The LLM literally reads "Type name: invoice, internal_document..." and uses it to decide what to put in that field. Your schema is your prompt.

workflow.py 
1import asyncio
2from tqdm.asyncio import tqdm_asyncio

8async def extract_structure_docs(pdf_dir:Path, temp_dir:Path):

10    tasks = []

21    base_dir = Path(__file__).parent.resolve() / "data"
22    pdf_dir = base_dir / "samples"
23    temp_dir = base_dir / "temp_files"
24    results_dir = base_dir / "results"
25    results_dir.mkdir(exist_ok=True)  # Create results folder if it doesn't exist
26
27    filenames, results = await extract_structure_docs(pdf_dir, temp_dir)
28    save_results_to_json(filenames, results, results_dir)  # Persist structured JSON to disk
29
30if __name__ == "__main__":
31    start_time = time.perf_counter()
32    asyncio.run(workflow())  # asyncio.run() is the sync entry point that starts the async event loop
33    end_time = time.perf_counter() - start_time
34    print(f"Analysis took: {end_time:.1f} seconds")
🔑 asyncio.create_task vs asyncio.gather — what's the difference?
create_task(coro) schedules a coroutine to start running immediately in the background — the loop continues without waiting. gather(*tasks) suspends the current coroutine until ALL scheduled tasks are complete and collects their results. Together, they implement the fan-out / fan-in pattern: launch many parallel workers, then collect results.

Scenario 2 — Reliability Strategies
Schema Strategy: Use a Literal type constraint for file_type: file_type: Literal["invoice", "internal_document", "instruction", "other"]. This forces the LLM to pick from a fixed set of values — Pydantic will reject any other value and trigger a retry. Add "other" as the designated fallback for unknown documents so downstream logic can handle them gracefully.

Instructions Strategy: Add explicit fallback guidance to the agent's system prompt: "If you cannot confidently identify the document type, always return 'other' for file_type. Never return an empty string." Instructions give the LLM policy guidance before it even generates; the schema then enforces the constraint as a hard constraint.
Scenario 3 — Cost vs. Accuracy
Risks of single-agent approach: Task interference — when a single model must simultaneously classify AND extract, it can make errors in extraction that would have been avoided if extraction was guided by a clear category label. The model may bias its extraction toward the wrong schema if classification is uncertain. The prompt becomes more complex, increasing the chance of format errors.

When single-agent is acceptable: (1) Documents are highly uniform and easy to classify — e.g., a pipeline that only ever processes invoices makes classification trivial. (2) The LLM being used is very capable (e.g., GPT-4o) and the document schemas are simple with few fields. (3) Cost sensitivity significantly outweighs accuracy requirements — e.g., a bulk preprocessing pipeline where some extraction errors are acceptable and can be filtered downstream. (4) Latency matters and eliminating one API round-trip is critical.
