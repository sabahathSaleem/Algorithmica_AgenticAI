Section 01

Core Concepts

The mental models you need before the code makes sense.

🖥️

CPU — Latency Optimized

CPUs have a few powerful cores (8–64 in typical machines). Each core is super-fast at complex, sequential tasks. They handle branching, decision-making, and general OS work. But they can only do a handful of things at once.

8–64 beefy cores
🎮

GPU — Throughput Optimized

GPUs have thousands of tiny cores (CUDA cores). Each is slower than a CPU core, but they all run in parallel. Perfect for repetitive math operations on large data — like multiplying every element in a huge matrix simultaneously.

4000–18000+ CUDA cores
🧠

CUDA — GPU Programming API

CUDA (Compute Unified Device Architecture) is NVIDIA's framework for running code on GPU. A CUDA core is one processing unit. They're grouped into Streaming Multiprocessors (SMs) — think of SMs as small CPU-like clusters, each holding 64–192 CUDA cores.

NVIDIA only
🔥

PyTorch Tensors

A Tensor is a multi-dimensional array (like NumPy). The magic: add device='cuda' and PyTorch automatically moves the data to GPU memory and runs operations there. The same code runs on CPU or GPU — just change the device string.

torch.randn(size, device=...)
⏱️

GPU Synchronization

GPUs run asynchronously — when you call torch.matmul() on a GPU, the CPU returns immediately (before GPU is done!). torch.cuda.synchronize() forces the CPU to wait for the GPU to fully finish — critical for accurate timing.

Without it: times are wrong!
📐

Matrix Multiplication as Benchmark

MatMul (A × B) is the core operation of deep learning — every neural network layer is mostly matrix multiplications. Benchmarking it shows exactly how fast hardware is at AI work. Size matters: at 128×128, both CPU and GPU are fast; at 8192×8192, the difference is staggering.

O(n³) operations
💡 Why This Code Matters for GenAI

Every LLM inference call — every time you ran agent.run_sync() in the previous files — is powered by massive matrix multiplications. Understanding CPU vs GPU performance explains why cloud GPUs respond in milliseconds while a CPU would take minutes for the same model. This is the hardware foundation of all AI.

🔍 What get_cuda_cores() does step by step

1. cuda.select_device(0) — tells Numba which physical GPU to inspect.
2. MULTIPROCESSOR_COUNT — hardware register, returns the number of SMs on this GPU.
3. device.compute_capability — returns a tuple like (8, 6) for Ampere.
4. Dictionary lookup CC_CORES_PER_SM[(8,6)] → 128.
5. Multiply: 128 × 82 = 10,496 total CUDA cores. That's the final answer.

Section 05

How Benchmarking Is Done Right

The benchmark_matmul() function uses 3 professional techniques. Here's why each matters.

Execution Timeline for GPU Benchmark
PHASE 1
Warmup Run
← NOT timed. Forces GPU to load kernels & JIT-compile.
PHASE 2
sync()
← Wait for warmup to fully complete on GPU
REPEAT × 10 (num_runs)
start timer
perf_counter()
← High-resolution timer. More accurate than time.time()
compute
torch.matmul(A, B)
← GPU runs asynchronously here!
sync GPU
synchronize()
← CPU waits here until GPU is truly done
stop timer
perf_counter()
← Now we know REAL elapsed time
average
np.mean(times)
← Average over 10 runs = stable result
⚡ The 3 Pro Techniques

1. Warmup run — First GPU call is always slow (kernel compilation, cache cold). Throw it away.
2. cuda.synchronize() — Without this, you'd measure near-zero time because the CPU returns before GPU finishes.
3. Average over N runs — Removes timing noise from OS scheduling and memory fluctuations.

Commented Code

The full file — every block explained in detail.

cpu-gpu.py PYTORCH + NUMBA BENCHMARK 
# ─── IMPORTS ──────────────────────────────────────────────────────────────────
import torch
# PyTorch: the core ML framework. Handles tensors on both CPU and GPU.
# Key feature: same code runs on 'cpu' or 'cuda' — just change device string.

import time
# Standard library for timing. We'll use time.perf_counter().
# perf_counter() is more precise than time.time() — uses hardware timer.

import numpy as np
# NumPy: used only for np.mean(times) — average the 10 timing runs.
# The actual math happens in PyTorch, not NumPy.

from tabulate import tabulate
# Third-party library: pretty-prints a list of lists as a formatted table.
# Install: pip install tabulate

import os
# Used for os.cpu_count() — returns number of logical CPU cores.

from numba import cuda
# Numba: JIT-compiles Python to run on NVIDIA GPU.
# Here we only use it to QUERY hardware info (SM count, compute capability).
# Numba directly reads GPU hardware registers — PyTorch can't do this alone.


# ─── COMPUTE CAPABILITY → CORES/SM LOOKUP TABLE ───────────────────────────────
CC_CORES_PER_SM = {
    (2,0) : 32,  (2,1) : 48,   # Fermi (2010) — very old
    (3,0) : 192, (3,5) : 192, (3,7) : 192,  # Kepler (2012)
    (5,0) : 128, (5,2) : 128,  # Maxwell (2014)
    (6,0) : 64,  (6,1) : 128,   # Pascal (2016) — GTX 1080
    (7,0) : 64,  (7,5) : 64,    # Volta/Turing (2018) — RTX 2080
    (8,0) : 64,  (8,6) : 128, (8,9) : 128,  # Ampere (2020) RTX 3xxx / Ada RTX 4xxx
    (9,0) : 128,  # Hopper (2022) — H100, datacenter AI GPU
    (10,0): 128, (12,0): 128  # Blackwell (2024) — RTX 5090
}
# Key = (major, minor) compute capability tuple
# Value = CUDA cores per Streaming Multiprocessor
# Note: Turing (7.5) has 64 cores/SM despite newer Ampere (8.6) having 128
# NVIDIA doesn't always increase this linearly — architecture tradeoffs.


# ─── FUNCTION: GET TOTAL CUDA CORES ───────────────────────────────────────────
def get_cuda_cores(gpu_index=0):
    # gpu_index: which GPU to inspect (0 = first GPU, useful in multi-GPU systems)

    cuda.select_device(gpu_index)
        # Numba: "I want to talk to GPU #gpu_index"
        # Required before calling get_current_device()

    device = cuda.get_current_device()
        # Returns a Numba device object — has hardware properties as attributes

    sms = getattr(device, 'MULTIPROCESSOR_COUNT')
        # getattr() safely reads the MULTIPROCESSOR_COUNT hardware register.
        # This is the number of SMs (Streaming Multiprocessors) on the chip.
        # Example: RTX 3090 → 82 SMs

    cc_major, cc_minor = device.compute_capability
        # Tuple unpacking: compute_capability = (8, 6) for RTX 3090
        # cc_major=8, cc_minor=6 → Ampere architecture

    cores_per_sm = CC_CORES_PER_SM.get((cc_major, cc_minor))
        # Dictionary lookup. .get() returns None if key is missing (no crash)
        # New GPU architectures released after this code was written → None

    if cores_per_sm is None:
            # Guard clause: don't multiply by None — return helpful error message
        return f"Unknown compute capability: {cc_major}.{cc_minor}. Core count not in dictionary."

    total_cores = cores_per_sm * sms
        # Final formula: cores/SM × number of SMs = total CUDA cores on chip
        # Example: 128 × 82 = 10,496 CUDA cores (RTX 3090)
    return total_cores


# ─── FUNCTION: BENCHMARK MATRIX MULTIPLICATION ────────────────────────────────
def benchmark_matmul(size, device, num_runs=10):
    """
    Benchmark matrix multiplication for a given size and device
    """
        # Parameters:
    #   size     — matrix is size×size (e.g., 2048 → 2048×2048 matrix)
    #   device   — string: 'cpu' or 'cuda'
    #   num_runs — how many times to repeat for averaging (default: 10)

    matrix1 = torch.randn(size, size, device=device)
    matrix2 = torch.randn(size, size, device=device)
        # torch.randn() creates a matrix filled with random float32 values
        # (Gaussian distribution, mean=0, std=1)
        # device='cuda' → data lives in GPU VRAM (fast for GPU ops)
        # device='cpu'  → data lives in RAM (accessible to CPU cores)
        # For 8192×8192 float32: each matrix = 8192² × 4 bytes = 268 MB!

        # ── WARMUP RUN ──────────────────────────────────────────────────────
    torch.matmul(matrix1, matrix2)
        # The FIRST GPU call is always unusually slow because:
        #   1. CUDA kernel must be JIT-compiled for this specific input size
        #   2. GPU caches are cold (cache miss on first access)
        #   3. cuBLAS (NVIDIA's math library) may need to select an algorithm
        # If we timed this, the result would be misleadingly slow.
        # Solution: run once (throw away), then start timing.

    if device == 'cuda':
        torch.cuda.synchronize()
        # Wait for the warmup to FULLY finish on the GPU before timing begins.
        # GPU calls are fire-and-forget from CPU's perspective.
        # Without this, the actual benchmark could start before warmup is done.

        # ── TIMING LOOP ─────────────────────────────────────────────────────
    times = []
    for _ in range(num_runs):
                # _ means "I don't care about the loop variable" (Python convention)

        start = time.perf_counter()
                # perf_counter() = high-resolution timer (nanosecond precision)
                # Better than time.time() which has ~1ms resolution
                # Better than timeit for one-shot measurements

        torch.matmul(matrix1, matrix2)
                # The actual operation we're measuring.
                # CPU: runs on all available cores (uses OpenBLAS/MKL internally)
                # GPU: launches thousands of CUDA threads on GPU cores simultaneously

        if device == 'cuda':
            torch.cuda.synchronize()
                # ⚠️ CRITICAL: GPU runs ASYNCHRONOUSLY.
                # Without synchronize(), perf_counter() would measure near-0 time
                # because the CPU returns from matmul() before GPU is finished!
                # synchronize() = "CPU, wait here until GPU queue is empty"

        end = time.perf_counter()
        times.append(end - start)
                # Record elapsed seconds for this run

    return np.mean(times)
        # Average over num_runs=10 measurements.
        # This smooths out OS scheduling jitter, memory bandwidth fluctuations, etc.
        # A single run might be 20% off; an average of 10 is stable to ~2%.


# ─── FUNCTION: RUN ALL BENCHMARKS ─────────────────────────────────────────────
def run_benchmarks():
    sizes = [128, 512, 2048, 8192, 12288]
        # Exponentially growing sizes to show scaling behavior:
        # 128   → tiny  (fits in L2 cache)       → GPU overhead dominates
        # 512   → small (fills cache)             → GPU starts winning
        # 2048  → medium (spills to RAM/VRAM)     → GPU clearly faster
        # 8192  → large (267MB per matrix!)       → GPU wins massively
        # 12288 → huge  (needs 16GB+ VRAM)        → peak GPU advantage

    results = []

    for size in sizes:
        cpu_time = benchmark_matmul(size, 'cpu')
                # Always benchmark CPU — this works on any machine

        if torch.cuda.is_available():
                        # Check if CUDA is available before using GPU
                        # Returns False on machines without NVIDIA GPU or CUDA drivers
            gpu_time = benchmark_matmul(size, 'cuda')
            speedup = cpu_time / gpu_time
                        # speedup = how many times faster GPU is vs CPU
                        # speedup=100 means GPU did it 100× faster
            results.append([
                f"{size}x{size}",
                f"{cpu_time:.6f}s",   # 6 decimal places (microsecond precision)
                f"{gpu_time:.6f}s",
                f"{speedup:.2f}x"     # e.g., "147.23x"
            ])
        else:
            results.append([f"{size}x{size}", f"{cpu_time:.6f}s", "N/A", "N/A"])
                        # Graceful fallback: still show CPU results even without GPU

    print(tabulate(results, headers=["Matrix Size", "CPU Time (Avg)", "GPU Time (Avg)", "GPU Speedup"]))
        # tabulate() formats the list-of-lists into a clean ASCII table:
        # | Matrix Size | CPU Time (Avg) | GPU Time (Avg) | GPU Speedup |
        # |-------------|----------------|----------------|-------------|
        # | 128x128     | 0.000234s      | 0.000198s      | 1.18x       |
        # | 8192x8192   | 12.453210s     | 0.082341s      | 151.24x     |


# ─── ENTRY POINT ──────────────────────────────────────────────────────────────
if __name__ == "__main__":
        # Standard Python pattern: only run this block when executing THIS file
        # If another file does "import cpu-gpu", this block is skipped.
        # Allows the functions above to be reused as a library.

    if torch.cuda.is_available():
        print("GPU (CUDA) is available. Benchmarking both CPU and GPU.")
        print("CPU Cores:", os.cpu_count())
                # os.cpu_count() = logical cores (includes hyperthreading)
                # 8-core i9 with HT → reports 16

        gpu_count = torch.cuda.device_count()
        print(f"Total GPUs detected: {gpu_count}")
                # Supports multi-GPU setups (e.g., 4× A100 in a datacenter)

        for i in range(gpu_count):
            print(f"GPU {i} Name: {torch.cuda.get_device_name(i)}")
                        # e.g., "NVIDIA GeForce RTX 4090"

            cores = get_cuda_cores(i)
            print(f"GPU {i} CUDA Cores: {cores}")
                        # e.g., "GPU 0 CUDA Cores: 16384"
    else:
        print("GPU (CUDA) not available. Benchmarking CPU only.")
        print("Install a CUDA-enabled PyTorch version to test GPU performance.")
        print("CPU Cores:", os.cpu_count())

    run_benchmarks()
        # Start the actual benchmark — runs for several minutes on large matrices!

GPT-4 has ~1.8 trillion parameters organized in matrices. Every token you send gets multiplied through hundreds of these matrices. A single forward pass = trillions of MatMul operations.

The 12288×12288 matrix in this benchmark is exactly the hidden dimension size of GPT-3/4 class models. The 466× speedup you see here is why inference on a GPU takes milliseconds, while CPU would take minutes per token.

When you called agent.run_sync() in the previous files and got an answer in 1–2 seconds? That's thousands of these matrix multiplications happening in parallel on a cloud GPU farm.

⚠️

When GPU Loses (Small Matrices)

At 128×128, GPU is only ~1.2× faster (or even slower!). The overhead of launching GPU kernels, transferring data, and synchronizing costs more than the actual math. GPUs need big data to amortize that overhead.

overhead > speedup
📦

Libraries Inside PyTorch

When you call torch.matmul(), PyTorch calls cuBLAS (NVIDIA's hand-optimized BLAS library) — not raw CUDA cores. cuBLAS uses Tensor Cores (specialized hardware for 4×4 matrix ops) on Volta+ GPUs — even faster than CUDA cores alone.

cuBLAS → Tensor Cores
