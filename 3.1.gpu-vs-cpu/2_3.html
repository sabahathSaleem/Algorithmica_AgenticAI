Chapter 1 — The Big Picture

What is Agentic AI?

You know how a traditional ML model takes an input and returns a prediction in one shot? An Agentic AI is different — it's an LLM-powered system that can reason, plan, decide, and act over multiple steps to complete a complex goal.

Think of it like the difference between asking a calculator to multiply two numbers versus hiring an analyst to research, calculate, and write a report — the analyst orchestrates their own steps.

📖 Definition — Agent

An Agent is an LLM that can perceive inputs, choose actions (like calling functions or tools), observe results, and iterate — all without needing you to manually script each step. The LLM itself acts as the "brain" deciding what to do next.

Chapter 3 — Concept Explainers

Key Concepts, From the Ground Up

🔷 Pydantic Models as a "Contract"

In traditional Python, if you ask an LLM something, you get back a string. That's unpredictable — the model might say "Sure! Here is the info:" and write prose instead of a clean data field.

Pydantic is a Python library that lets you define a data schema — like a strict template. When you pair this with an Agent, the LLM is forced to fill in that template rather than improvise.

📖 Definition — Pydantic BaseModel

A BaseModel is a Python class that declares typed fields. When used as an output_type in PydanticAI, the framework automatically generates a JSON schema from your class and instructs the LLM to produce output that matches it. Pydantic then validates the response and raises an error if it doesn't comply.

Without Schema

"India is a country in Asia. It has many rivers like the Ganges..."

Unstructured — hard to parse programmatically.

With Pydantic Schema

continent_name: "Asia"
country_name: "India"
has_river: true

Machine-readable, validated, and predictable.

🔷 Annotated + Field: The Constraint System

Annotated[str, Field(description="...")] is how you communicate intent to the LLM. The Field object carries metadata that becomes part of the JSON schema sent to the model. Think of it as writing inline instructions directly into your data contract.

💡 Key Insight

The description inside Field() isn't just for developers — the LLM reads it too. It tells the model exactly what should go in that field. This is how you "prompt engineer" at the schema level, not just the system prompt level.

🔷 Literal Types for Classification

Literal["general", "order", "billing"] restricts the type system to only those three string values. The JSON schema sent to the LLM includes an enum constraint, so the model cannot hallucinate a new category. This is Agentic AI's answer to uncontrolled open-ended generation.

⚠️ Common Misconception

Just having Literal doesn't mean the LLM is "choosing" in a deep reasoning sense — it's being constrained at the JSON schema level. Real classification agents reason about ambiguous text, but Literal types give you a controlled, deterministic output space.

🔷 Nested Models = Hierarchical Structure

The Plan model contains a list[SubTask], and each SubTask has its own fields. This nesting makes the agent produce a structured plan with multiple components — not just a flat answer. This mirrors how planning agents decompose goals into sub-goals.

✅ Why This Matters for Agentic AI

Nested structured output is the foundation of Planning Agents. By forcing the model to produce an ordered list of typed subtasks, you get programmatic access to every step — you can then execute those steps sequentially, passing results forward (a pipeline/chain architecture).

🔷 Observability with Logfire

logfire.instrument_pydantic_ai() hooks into every agent call to record traces — inputs, LLM calls, token usage, outputs. This is critical for Agentic AI because agents make dynamic decisions you can't predict in advance. Without observability, debugging is nearly impossible.

💡 Observability ≠ Logging

Standard logs tell you what happened. Observability tools like Logfire tell you why, how long, how many tokens, and let you trace chains of LLM calls. For agents that run many steps, this is your primary debugging interface.

🔷 run_sync: Synchronous Execution

agent.run_sync(prompt) calls the LLM synchronously — the program waits for the response before continuing. PydanticAI also supports agent.run() for async workflows. For production pipelines, async is preferred; for scripts and learning, sync is simpler.

🔷 Multi-Provider Design

The Agent('groq:llama-3.3-70b-versatile', ...) or Agent('ollama:qwen3:4b', ...) syntax shows that PydanticAI abstracts over LLM providers. The same agent code works whether you swap to OpenAI, Groq, Ollama, or Gemini — provider-agnostic agent code is a major architectural win.

Line-by-Line Deep Dive

Annotated Explanations

L1–2

Typing Imports Standard

Annotated is from Python's typing module. It lets you attach extra metadata to a type hint — here, that metadata is a Pydantic Field with instructions for the LLM. Think of it as: Annotated[type, "instructions for whoever reads this"].

L3

PydanticAI Agent Import Agent Logic

This is the heart of the framework. Agent is a class that wraps an LLM provider, a system prompt, and an output schema into a single callable unit. It handles the entire lifecycle: prompt construction → LLM call → response parsing → validation.

L8–9

Observability Setup Standard

logfire.configure() initializes the connection to Pydantic's Logfire dashboard. instrument_pydantic_ai() patches the framework to automatically emit spans for every Agent call — you get token counts, latency, inputs, and outputs with zero manual instrumentation.

L11–19

SubTask Schema Schema

SubTask is the "leaf node" of the plan. The ge=1 constraint on task_id means Pydantic will raise a ValidationError if the LLM returns 0 or a negative number. The min_length=1 on description prevents empty strings. These constraints run after the LLM responds — Pydantic validates the parsed JSON.

L21–29

Plan Schema (Nested Model) Schema

This is the key architectural move: tasks: list[SubTask] creates a one-to-many relationship in the schema. The LLM must produce a JSON array where every element matches the SubTask schema. This is how you get structured multi-step plans from a single prompt. The goal field captures the agent's understanding of the overall objective.

L32–37

Agent Definition — Where the Magic Happens Agent Logic

Three key parameters: (1) The model string — 'groq:llama-3.3-70b-versatile' — tells PydanticAI which provider and model to use (provider:model format). (2) instructions becomes the system prompt. (3) output_type=Plan is where schema grounding happens — PydanticAI converts your Pydantic class into a JSON Schema and appends it to the LLM's instructions, forcing structured output. The commented-out Ollama line shows provider flexibility.

L40

run_sync — Agent Invocation Agent Logic

run_sync is a synchronous wrapper around the async LLM call. Internally it: (1) builds the full prompt (system + user + schema instructions), (2) calls the LLM API, (3) parses the JSON response, (4) validates it against Plan, (5) retries with error feedback if validation fails, (6) returns an AgentRunResult wrapping the valid Plan object.

L42–43

Accessing Results Standard

response.output is a real Plan Python object — you can access response.output.goal or loop over response.output.tasks as actual SubTask instances. response.usage() returns token counts (input tokens, output tokens, total cost) — essential for production cost monitoring.

✅ Answer Key

Q1 — output_type parameter
Correct: B

The output_type triggers PydanticAI to convert your Pydantic class into a JSON Schema and inject it as additional instructions to the LLM. The framework then parses the LLM's response and validates it against the schema, raising errors (and optionally retrying) if validation fails. This is fundamentally different from just setting a prompt.

Q2 — Literal types
Correct: B

Literal in Python's type system maps directly to JSON Schema's enum. PydanticAI includes this constraint in the schema sent to the LLM. Post-response, Pydantic validates that the returned value is one of the allowed strings — so you get both a model-level hint and a code-level enforcement.

Q3 — logfire.instrument_pydantic_ai()
Correct: B

This function monkey-patches PydanticAI's internal methods to automatically emit OpenTelemetry spans. Every Agent call becomes a traceable event in Logfire's dashboard — no manual logging needed. This is critical for debugging non-deterministic LLM behavior in production.

Q4 — list[Step] in Reasoning model
Correct: C

This is structured Chain-of-Thought. Instead of the LLM reasoning in freeform text (which you can't inspect programmatically), each reasoning step is captured as a Step object with typed fields. You can serialize, log, display, or even validate individual reasoning steps.

Q5 — Field(description=...) purpose
Correct: B

Pydantic's JSON Schema generation includes field descriptions in the "description" property of each schema property. LLMs read this schema as part of their instructions, so your field description is literally a prompt to the model about what to generate. This is "schema-level prompt engineering."

Q6 — Customer Support Classification Schema
Model Answer:

Define a TicketCategory Pydantic model with a category field typed as Annotated[Literal["account", "bug", "refund", "general"], Field(description="Category of the customer support ticket")]. Create an Agent with output_type=TicketCategory and a system prompt like "Classify the customer message into exactly one category." The Literal constraint ensures the model can never hallucinate a fifth category. Optional enhancement: add a confidence: float field with ge=0.0, le=1.0 constraints for soft routing logic.

Q7 — PydanticAI vs. manual json.loads()
Model Answer (any 2 of these):

(1) Automatic validation: PydanticAI validates the LLM's JSON against your schema and can auto-retry with error feedback if it fails, whereas manual parsing crashes on bad output with no recovery path. (2) Type safety: You get a typed Python object (Plan, not a dict), so your IDE provides autocomplete, and runtime attribute access is safe. (3) Schema as documentation: The Pydantic model is simultaneously the schema, the validator, and the docs — one source of truth. (4) Constraint enforcement: Field constraints (ge=1, min_length, Literal) are automatically applied, whereas manual parsing requires writing your own validation logic.

Q8 — Executing a Generated Plan
Model Answer:

After response = agent.run_sync(user_prompt), access response.output.tasks (a list[SubTask]). Loop: for subtask in response.output.tasks: and process subtask.description. Each iteration could: (1) pass the description to a specialized "executor agent" with appropriate tools, (2) call an external API if the task maps to a known function, (3) log progress with subtask.task_id as a trace key. Results can be accumulated and passed as context to the next subtask — this is the foundation of a sequential multi-agent pipeline or a ReAct loop.
