Core Concepts

New territory — everything in this file is about watching your AI, not just running it.

🔥

Logfire — What Is It?

A cloud observability platform built by the Pydantic team (same people who made pydantic_ai). It collects, stores, and visualises traces from your application in a live web dashboard. Think of it as Google Analytics, but for AI agent calls.

pydantic.dev/logfire
📡

OpenTelemetry (OTel)

The open-source standard for collecting telemetry (traces, metrics, logs) from applications. Logfire is built on top of OTel — it uses the OTel SDK to instrument code and the OTel protocol (OTLP) to ship data to the cloud. Industry-standard, vendor-neutral.

CNCF open standard
🕰️

Traces & Spans

A trace is a complete record of one operation (e.g., one agent.run_sync() call). A span is a timed unit inside that trace — like "sending to Groq API" or "parsing response". Spans nest like a call stack, giving you a flamegraph of your agent's execution.

root → child spans
⚡

Auto-Instrumentation

logfire.instrument_pydantic_ai() is monkey-patching — it rewrites pydantic_ai's internals at runtime to inject tracing code. You don't touch any of your agent code. One call and every future run_sync() is automatically observed.

zero code change needed
🪙

Token Cost Tracking

Logfire captures response.usage() data — prompt tokens, completion tokens, and total — from every single call and aggregates them over time. This turns "how much did I spend this week?" from a mystery into a precise dashboard metric.

per-call + aggregate
🚨

Latency & Error Alerting

Every span has a start time and end time → Logfire knows exactly how long each LLM call took. If a call fails, the error is captured in the trace with the full stack trace. You can set alerts on latency thresholds or error rates.

P50 / P95 / P99

Because Logfire uses standard OTel, you could also export traces to Jaeger, Honeycomb, Grafana Tempo, Datadog, or any other OTel-compatible backend — same code.
🔍 What is OTLP?

OTLP (OpenTelemetry Protocol) is the standard wire format for sending trace data. It uses Protocol Buffers (protobuf) over HTTP or gRPC — a compact binary format much faster than JSON. When Logfire calls logfire.configure(), it sets up an OTel exporter that batches spans and ships them via OTLP to Logfire's cloud endpoint, authenticated with your LOGFIRE_TOKEN.

⏱️ Why Nested Spans Are Powerful

When your agent slows down, is it the network call to Groq? The prompt construction? Or the response parsing? Without spans, you know "it was slow". With spans, you know exactly which 4 milliseconds to fix. The flamegraph view in Logfire's dashboard makes this visually instant — no digging through logs.

💰

Tokens in the model's response — usually priced higher than input tokens.
gen_ai.usage.output_tokens → 41
🤖

Which model was used — useful when you have multiple agents using different models.

🏭

Which LLM provider served the request (Groq, OpenAI, Ollama, etc.).

🚨
Errors & Exceptions

error.type → RateLimitError
🔁
Retry Count
If pydantic_ai retries a failed call, each attempt is a separate child span with its outcome.
pydantic_ai.attempt → 1, 2…
🌐 OTel Semantic Conventions

Notice the attribute names like gen_ai.usage.input_tokens — these follow OpenTelemetry Semantic Conventions for GenAI, a shared naming standard so any observability tool can parse and display LLM traces consistently. Logfire, Honeycomb, Grafana, Datadog — they all understand these attribute names. Your traces are portable.

Section 06

Commented Code

The full script — every line explained with production context.

logfire_integration.py OBSERVABILITY · AUTO-TRACE 
# ─── IMPORTS ─────────────────────────────────────────────────────────────────
from dotenv import load_dotenv
# Reads .env file into os.environ.
# Required for TWO keys this time:
#   GROQ_API_KEY   → pydantic_ai uses this for the LLM provider
#   LOGFIRE_TOKEN  → logfire.configure() uses this to authenticate with Logfire cloud
# Without LOGFIRE_TOKEN, configure() will fail or send traces nowhere.

from pydantic_ai import Agent
# Same Agent we've used every week.
# IMPORTANT: The agent code itself is UNCHANGED even though we add observability.
# Logfire hooks into pydantic_ai's internals — your agent is unaware it's being traced.

import logfire
# Pydantic's observability SDK. Built on top of OpenTelemetry.
# Install: pip install logfire[pydantic-ai]
# The [pydantic-ai] extra installs the pydantic_ai instrumentation plugin.
# Without the extra: logfire.instrument_pydantic_ai() won't exist!


# ─── LOAD ENVIRONMENT ────────────────────────────────────────────────────────
load_dotenv(override=True)
# Standard: loads .env → os.environ.
# CRITICAL ORDER: must happen BEFORE logfire.configure()
# because configure() reads LOGFIRE_TOKEN from os.environ at call time.


# ─── LOGFIRE SETUP ───────────────────────────────────────────────────────────
logfire.configure()
# Initialises the full OpenTelemetry pipeline:
#
#   1. Reads LOGFIRE_TOKEN from os.environ
#      → this authenticates your telemetry to YOUR Logfire project
#
#   2. Creates an OTLP exporter
#      → a background thread that batches spans and ships them
#      → destination: https://logfire-api.pydantic.dev/v1/traces
#      → format: protobuf over HTTP (compact + fast)
#
#   3. Sets up a global OTel TracerProvider
#      → now any OTel-aware library (pydantic_ai, httpx, etc.)
#      → can create spans that automatically flow to Logfire
#
# Optional args (not used here but good to know):
#   logfire.configure(service_name='my-agent')  → label in dashboard
#   logfire.configure(send_to_logfire=False)     → dev mode, print only
#   logfire.configure(environment='production')  → tag traces by env

logfire.instrument_pydantic_ai()
# THE MAGIC LINE. This is auto-instrumentation via monkey-patching:
#
#   - At runtime, this function modifies pydantic_ai's Agent internals
#   - It wraps the LLM call methods with OTel span creation
#   - Every future agent.run_sync() / agent.run() call will:
#       → open a root span at entry
#       → open child spans for each internal step (prepare, LLM call, parse)
#       → record prompt, response, tokens, model, provider as span attributes
#       → close spans on exit (or record exception on error)
#
# MUST be called AFTER logfire.configure() — needs the TracerProvider ready.
# MUST be called BEFORE creating Agent() — instruments the class, not instances.
# (Actually it instruments at the call level so order vs Agent() matters less,
#  but best practice: configure → instrument → create agent → run)


# ─── CREATE AGENT ────────────────────────────────────────────────────────────
agent = Agent(
    'groq:llama-3.3-70b-versatile',
        # By-name string. pydantic_ai reads GROQ_API_KEY from env automatically.
    # Nothing changed here from Week 1 — same one-liner.

        #'ollama:llama3-groq-tool-use:8b',
    # Commented alternative: local Ollama model fine-tuned by Groq for tool use.
    # 'llama3-groq-tool-use' = a version of LLaMA3 trained to call functions reliably.
    # Useful when you need function calling locally without cloud costs.
    # With Logfire: local Ollama calls are ALSO traced — Logfire sees all providers.

    instructions="You are a helpful assistant.",
)
# The agent has NO knowledge of Logfire. It's just an Agent.
# Logfire wrapped its internals before this was even instantiated.


# ─── QUERY 1: Creative task ──────────────────────────────────────────────────
response = agent.run_sync("Write a haiku about recursion in programming.")
# What happens invisibly thanks to instrument_pydantic_ai():
#
#   [Logfire] → SPAN OPEN: pydantic_ai.agent.run
#     attributes: {gen_ai.prompt: "Write a haiku…", gen_ai.system: "groq"}
#
#   [pydantic_ai] → prepares messages list: [system_prompt, user_message]
#   [pydantic_ai] → calls Groq HTTP API
#
#     [Logfire] → CHILD SPAN OPEN: groq.chat.completions.create
#       records: HTTP method, URL, request headers (sanitised)
#       waits for Groq to respond (this is the slow part)
#     [Logfire] → CHILD SPAN CLOSE: records response, status 200
#
#   [pydantic_ai] → parses response into RunResult
#
#   [Logfire] → SPAN CLOSE: pydantic_ai.agent.run
#     attributes: {
#       gen_ai.completion: "",
#       gen_ai.usage.input_tokens: 28,
#       gen_ai.usage.output_tokens: 41,
#       duration_ms: 1241
#     }
#
# All of this shipped in background to Logfire dashboard. Your code sees none of it.

print(response.output)
    # Still prints to console — local debugging unchanged.
print(response.usage())
    # Still prints usage — and Logfire ALSO captured this independently.
    # Two sources of truth: your console + the Logfire dashboard.


# ─── QUERY 2: Analytical task ────────────────────────────────────────────────
response = agent.run_sync("What are the top 3 best practices for writing clean code?")
# Second completely independent traced call.
# In Logfire dashboard: you'll see TWO separate root spans — one per run_sync().
# You can compare them: haiku call vs best-practices call.
# Which used more tokens? Which was slower? Which prompt cost more?
# Dashboard answers this in 2 seconds flat.

print(response.output)
print(response.usage())

Setup Checklist — Getting Logfire Running

1

Create a Logfire Account

Go to logfire.pydantic.dev → sign up with GitHub → create a project → copy your LOGFIRE_TOKEN from project settings.

2

Add Token to .env

Add LOGFIRE_TOKEN=your_token_here to your .env file alongside GROQ_API_KEY. Never commit this to Git.

3

Install the Extra

pip install "logfire[pydantic-ai]" — the [pydantic-ai] extra is required for instrument_pydantic_ai() to exist.

4

Run the Script → Watch the Dashboard

Open the Logfire dashboard in your browser, run the script in terminal. Traces appear in the dashboard in real-time as the script executes.

Logging vs Tracing — Know the Difference

Both capture events — but traces give you structure logging never could.

As your agents get more complex — Tool calls (agent calls a Python function), Multi-turn conversations, Multi-agent pipelines — Logfire becomes even more essential. Each tool call becomes a child span. You see: which tool was called, with what arguments, and what it returned. A 10-step agent creates a 10-level span tree — and you can see every step in the dashboard in perfect detail. Observability is not optional at that scale.
