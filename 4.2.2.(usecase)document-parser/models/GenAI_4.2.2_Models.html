🗺 What Are These Files, Really?

🧾 Think of every Pydantic model as a printed form.

A tax form has fields: Name, PAN, Income, Deductions. You must fill in Name and PAN (required). You may leave some optional ones blank. If you write text in a Number field — the form is rejected.

These 5 Python files are exactly that — digital forms the AI must fill in. Pydantic is the "form validator" that checks if the AI's answers match the expected types.

Section 01
🧠 Core Concepts — Explained Like You're 13
📦

BaseModel — The Base Form

Every schema inherits from BaseModel. This gives it superpowers: automatic validation, JSON serialisation, and the ability to be understood by PydanticAI as an output schema.

🧒 Like: all official forms (passport form, visa form, bank form) share the same paper size and format rules. BaseModel is that shared "form standard".
🏷

Field(...) — Describing Each Slot

Field(...) adds metadata to a field: a description that guides the AI, a title for readability, and whether it's required (...) or optional (None / default value).

🧒 Like: a form field label that says "Date of Birth (DD/MM/YYYY)". The description tells you exactly what to write and in what format.
🔴

Required Fields: ... (Ellipsis)

field: str = Field(...) — the ... means no default value. The AI MUST provide this field. If it doesn't, Pydantic raises a ValidationError.

🧒 Like: a form field marked with a red asterisk ✱. You can't submit without filling it in. The ... is Python's asterisk.
🟢

Optional Fields: str | None = None

field: str | None = Field(None) — the field can be a string OR None (missing). The default is None so it doesn't fail if the AI doesn't find it in the document.

🧒 Like: a form field for "Middle Name" — most people leave it blank. That's fine. | None is saying "blank is acceptable".
🪆

Nested Models

A Pydantic model can contain other Pydantic models as fields. Invoice has a supplier: Party field — the entire Party object is nested inside. The AI must fill in the whole inner form too.

🧒 Like: a school application form that has a section "Parent Details" — which is itself a mini-form with Name, Phone, Occupation. Forms inside forms!
📋

list[Model] — Repeating Sections

line_items: list[LineItem] means "a list where every item is a LineItem object". An invoice may have 1 or 50 line items — all validated against the same schema.

🧒 Like: a shopping bill that has multiple rows. Each row has the same columns (item name, qty, price). list[LineItem] = that repeating row.
🔒

Literal[...] — Locked Choices

Literal["invoice", "payslip", "driver_license"] means the value MUST be exactly one of those three strings — nothing else. It's an enum without writing a full Enum class.

🧒 Like: a multiple-choice question with only 3 options. You can't write "contract" — the validator will reject it instantly.
🏷

Annotated[type, Field(...)]

An alternative way to attach Field metadata using Python's Annotated wrapper. Annotated[Literal[...], Field(description=...)] combines the type constraint AND the description in one clean expression.

🧒 Like: writing both the allowed answers AND the hint on a quiz question label instead of separately. Tidier.
📅

date type (from datetime)

Using Python's date type instead of str for dates means Pydantic automatically validates and parses the value as a real calendar date. "2024-01-15" → datetime.date(2024, 1, 15).

🧒 Like: a form that only accepts DD/MM/YYYY format and rejects "January 15th" or random text. Strict date checking for free!
🌊

float | None = 0.0 — Typed Optional with Default

The field can be a float OR None, and defaults to 0.0 if missing. This means "it's expected to be a number, but if the document doesn't have it, treat it as zero".

🧒 Like: a payslip field for "State Tax" — some states have no tax, so it defaults to 0 if missing from the document.
📝

Docstrings as Context

Every class has a docstring (the text in triple quotes). PydanticAI includes these in the JSON schema sent to the LLM. The AI reads them to understand what the model represents. Better docstrings = smarter AI.

🧒 Like: writing instructions at the top of a form: "This section is for the BUYER details, not the seller." Guides the AI to fill it correctly.
🏭

default_factory=list

For list fields, you can't use default=[] — Python would share that list across all instances (a classic bug). default_factory=list creates a fresh empty list for every new instance.

🧒 Like: giving every student their own blank notebook instead of making them all share one. Factory = "make a new one each time".

File 1 of 5 — Simplest
CATEGORY category.py

The "sorter" schema — just one field that must be exactly one of three allowed strings. Used by the classifier agent to label each document.

category.py
from typing import Annotated, Literal
# Annotated → attach extra info (like Field) to a type without changing it
# Literal   → restrict a str/int to specific fixed values only

from pydantic import BaseModel, Field


class DocumentCategory(BaseModel):
    """Docstring sent to LLM: 'supported classifications for financial and ID documents.'
    The AI reads this to understand the purpose of this model before filling it."""

    category: Annotated[
        Literal["invoice", "payslip", "driver_license"],
        # ☝️ Literal[...] = ONLY these 3 exact strings are valid.
        #    "contract", "receipt", "invoice " (extra space) → all REJECTED.
        Field(description="The category of the ticket")
        # ☝️ Field inside Annotated = alternative to field: type = Field(...)
        #    Cleaner when the type itself is complex (like Literal[...]).
    ]
    # ← No default value = REQUIRED. The AI must return exactly one of the 3 strings.
    # ← No = None, no = "", no = Field(...) with default. Just the type itself.
    # USAGE in agents_custom.py:
    #   classifier_response.output.category  →  "invoice" / "payslip" / "driver_license"
    #   classification_to_schema.get(category) → Invoice / Payslip / DriversLicense

💡 Why Literal Instead of Just str?

  • A plain str field lets the AI return "Invoice", "INVOICE", "bill" — all different
  • Literal[...] forces exact match — prevents routing bugs in the classifier
  • Pydantic generates an enum in JSON Schema from Literal — guides the AI perfectly

💡 Annotated vs Normal Field

  • Normal: category: str = Field(description="...")
  • Annotated: category: Annotated[str, Field(description="...")]
  • Both work — Annotated is preferred when type is complex like Literal[...]

GENERIC generic.py

Three models in one file — for the "analyse anything" approach. FileElement → ModelAnalysisOutput → OCROutput (wrapper). All fields optional with defaults.

generic.py
from pydantic import BaseModel, Field


# ═══ LEVEL 3 (innermost) — one element found on a page ════════════════════
class FileElement(BaseModel):
    """One detected element: a table, paragraph, image, heading, etc."""

    element_type: str = Field(
        description="Type of the element found on the page",
        default=""         # ← default="" means optional — no Validation Error if missing
    )
    element_content: str = Field(
        description="Content of the element found on the page",
        default=""
    )
    # EXAMPLE output: FileElement(element_type="table", element_content="| Col1 | Col2 |\n|---...")
    # EXAMPLE output: FileElement(element_type="paragraph", element_content="Dear customer...")


# ═══ LEVEL 2 — full page analysis result ═════════════════════════════════
class ModelAnalysisOutput(BaseModel):
    """What the LLM returns for generic document analysis — sent as output_type to Agent."""

    file_type: str = Field(
        description="e.g.: invoice, internal_document, instruction, other",
        default=""
    )
    file_content_md: str = Field(
        description="OCR output: full contents of the file in Markdown",
        default=""
        # ← Markdown format is useful for preserving tables, headers, lists
    )
    file_elements: list[FileElement] = Field(
        description="Elements detected: tables, images, paragraphs, graphs...",
        default_factory=list
        # ☝️ default_factory=list → creates a NEW [] for every instance.
        #    NEVER write default=[] for mutable defaults — shared state bug!
    )
    # ☝️ list[FileElement] = nested model list.
    #    PydanticAI generates JSON schema: array of objects matching FileElement.
    #    The AI must return a JSON array where each object has element_type + element_content.


# ═══ LEVEL 1 (outermost wrapper) — used by us, NOT sent to LLM ═══════════
class OCROutput(BaseModel):
    """We build this OURSELVES after the agent returns. Not the AI output_type."""

    filename: str = ""
    # ← Simple default field — no Field() wrapper needed for basic defaults

    analysis_result: ModelAnalysisOutput = Field(default_factory=ModelAnalysisOutput)
    # ☝️ default_factory=ModelAnalysisOutput → calls ModelAnalysisOutput() to make
    #    a fresh empty instance as the default. Same pattern as list but for a model.
    # USAGE in agents_generic.py:
    #   output = OCROutput(filename=image_path.stem, analysis_result=agent_result.output)

DRIVER'S LICENSE drivers_license.py

Flat model — no nesting, all 7 fields required. Uses Python's date type for automatic date validation and parsing.

drivers_license.py
from pydantic import BaseModel, Field
from datetime import date
# date → Python's built-in date type. Pydantic auto-parses "2024-01-15" → date(2024,1,15)
#         Also validates: "not-a-date" → ValidationError. Free format checking!


class DriversLicense(BaseModel):
    """Docstring: Personal identity + licensing details from a government-issued DL."""

    address: str = Field(
        ...,                                      # ← ... = REQUIRED. No default.
        title="Address",                         # title = human-readable label (for UI/docs)
        description="The address of the individual."  # description = guides the AI
    )

    date_of_birth: date = Field(
        ...,
        title="Date of Birth",
        description="The birthdate of the individual."
        # ☝️ date type: AI must return "YYYY-MM-DD" format string.
        #    Pydantic auto-converts it to a Python date object.
        #    Trying to store "15 Jan 1990" → Pydantic tries to parse it → may fail.
    )

    document_id: str = Field(
        ...,
        title="Document ID",
        description="The unique document ID for the driver's license."
        # License number / DL number — kept as str, not int, because it may have letters
    )

    expiration_date: date = Field(
        ...,
        title="Expiration Date",
        description="The expiration date of the driver's license."
    )

    family_name: str = Field(
        ...,
        title="Family Name",
        description="The family name (last name) of the individual."
    )

    given_names: str = Field(
        ...,
        title="Given Names",
        description="The given names (first and middle names) of the individual."
        # ← "given_names" (plural) — first + middle in one string e.g. "John Michael"
    )

    issue_date: date = Field(
        ...,
        title="Issue Date",
        description="The issue date of the driver's license."
    )
    # ⚠️ All 7 fields are required (...). If the DL image is unclear and the
    #    AI can't find even ONE field, the whole response fails validation.
    #    For production: consider making less-critical fields Optional[str] | None.

⚠️ All Required = Fragile

  • If the AI can't read the address (blurry image), the whole extraction fails
  • Consider str | None = None for fields that might be missing
  • Or add a try/except + retry mechanism in the calling agent

✅ date Type Advantage

  • Free format validation — "xyz" as a date raises ValidationError automatically
  • Serialises to ISO 8601 format ("2024-01-15") in JSON output
  • Can do date math: expiration_date - issue_date to get license age

PAYSLIP payslip.py

Flat model with 15 fields — a mix of required (core salary/tax fields) and optional (state tax, hours, hourly rate). Uses both date and float types.

payslip.py
from datetime import date
from pydantic import BaseModel, Field


class Payslip(BaseModel):
    """Payroll, tax withholding, and employment details from a payslip."""

    # ─── EMPLOYEE IDENTITY ─────────────────────────────────────────────────
    employee_id:   str = Field(..., description="Unique identifier for the employee")
    employee_name: str = Field(..., description="Full name of the employee")

    # ─── PAY PERIOD ────────────────────────────────────────────────────────
    pay_period_start: date = Field(..., description="Start date of the pay period")
    pay_period_end:   date = Field(..., description="End date of the pay period")
    payment_date:     date = Field(..., description="Date the payment was issued")
    # ☝️ Three distinct date fields:
    #    pay_period_start → when the work period started (e.g. 2024-01-01)
    #    pay_period_end   → when it ended (e.g. 2024-01-31)
    #    payment_date     → when the salary was deposited (e.g. 2024-02-05)

    # ─── EARNINGS ──────────────────────────────────────────────────────────
    gross_income: float = Field(..., description="Total income before deductions")
    net_income:   float = Field(..., description="Income after all deductions")
    # float used for money — though Decimal is more precise for financial data in prod!

    # ─── REQUIRED DEDUCTIONS ───────────────────────────────────────────────
    federal_tax:      float = Field(...,  description="Federal tax deduction")
    social_security:  float = Field(...,  description="Social Security deduction")
    medicare:         float = Field(...,  description="Medicare deduction")

    # ─── OPTIONAL DEDUCTIONS (region/contract dependent) ───────────────────
    state_tax:        float | None = Field(0.0, description="State tax, if applicable")
    other_deductions: float | None = Field(0.0, description="Other deductions (insurance, retirement)")
    # ☝️ float | None = Field(0.0) means:
    #    - The value CAN be a float OR None (missing)
    #    - Default is 0.0 (not required from AI)
    #    - Some states have no income tax (Texas, Florida) → field is genuinely 0

    # ─── OPTIONAL WORK DETAILS (salaried employees may not have these) ──────
    hours_worked: float | None = Field(
        None,                                   # ← default None (not 0.0)
        description="Total hours worked in the pay period"
        # None vs 0.0: None means "not applicable", 0.0 means "zero hours". Different!
    )
    hourly_rate:  float | None = Field(
        None,
        description="Employee's hourly rate, if applicable"
        # Salaried employees don't have hourly_rate — None is correct here
    )

INVOICE invoice.py

The richest schema — 4 nested sub-models (Address, Party, LineItem, VAT) + the Invoice parent. Mirrors the structure of a real business invoice. Notice how Party is reused for both supplier and receiver!

invoice.py
from pydantic import BaseModel, Field


# ═══ ADDRESS — reusable location block ═══════════════════════════════════
class Address(BaseModel):
    """Geographic location. All optional — not every invoice has full addresses."""
    street:      str | None = Field(None, description="Street address, e.g., 123 Main St")
    city:        str | None = Field(None, description="City, e.g., Springfield")
    state:       str | None = Field(None, description="State or province code, e.g., IL")
    postal_code: str | None = Field(None, description="Postal or ZIP code, e.g., 62704")
    country:     str | None = Field(None, description="Country, e.g., USA")
    # ⚠️ Address class is DEFINED but NOT used in Invoice!
    #    Invoice uses Party directly (Party has its own address fields).
    #    Address is likely a utility model for future use or other schemas.


# ═══ LINE ITEM — one product/service row on the invoice ══════════════════
class LineItem(BaseModel):
    """One item/service sold — the row in an invoice table."""

    amount:       float = Field(..., description="Total amount for this line item")
    description:  str   | None = Field(None, description="Product/service name, e.g., Laptop")
    product_code: str   | None = Field(None, description="SKU or product code, e.g., LPT-001")
    quantity:     int         = Field(..., description="Number of units")
    # ☝️ quantity is int, not float — you don't buy 2.5 laptops. Whole numbers only.
    unit:         str   | None = Field(None, description="Unit of measure, e.g., pcs")
    unit_price:   float       = Field(..., description="Price per single unit")
    # amount = quantity × unit_price (in theory — but AI extracts it, doesn't calculate)


# ═══ VAT — one tax row (invoices can have multiple tax rates) ════════════
class VAT(BaseModel):
    """A single VAT/tax entry — invoices can have multiple (e.g. 5% and 20%)."""

    amount:        float         = Field(...,  description="Taxable amount (before tax)")
    category_code: str | None   = Field(None, description="Tax category code, e.g., A")
    tax_amount:    float | None = Field(None, description="The calculated tax value")
    tax_rate:      float | None = Field(None, description="Percentage as float, e.g., 10 for 10%")
    total_amount:  float         = Field(...,  description="Total amount including tax")
    # amount + tax_amount = total_amount (extracted from doc, not calculated)


# ═══ PARTY — reused for BOTH supplier and receiver ════════════════════════
class Party(BaseModel):
    """Contact + ID details of a transacting entity — used twice in Invoice!
    Reusing one class for supplier AND receiver is clean DRY (Don't Repeat Yourself) design."""

    name:         str         = Field(...,  description="Entity name, e.g., Google")
    # ← name is required (the only one). Everything else is optional.
    street:       str | None = Field(None, description="Street address")
    city:         str | None = Field(None, description="City name")
    state:        str | None = Field(None, description="State or province")
    postal_code:  str | None = Field(None, description="Postal code")
    country:      str | None = Field(None, description="Country name")
    email:        str | None = Field(None, description="Contact email address")
    phone:        str | None = Field(None, description="Contact phone number")
    website:      str | None = Field(None, description="Entity website URL")
    tax_id:       str | None = Field(None, description="Tax identification number")
    registration: str | None = Field(None, description="Business registration number")
    iban:         str | None = Field(None, description="International Bank Account Number")
    payment_ref:  str | None = Field(None, description="Payment reference / invoice number")
    # ☝️ Party is the most "lenient" schema — only name required, rest optional.
    #    Real-world invoices vary wildly: some have IBAN, some don't. Optional = robust.


# ═══ INVOICE — the master container that ties everything together ══════════
class Invoice(BaseModel):
    """Top-level invoice schema. This is what agents_custom.py uses as output_type."""

    invoice_id:   str             = Field(..., description="Unique identifier of the invoice")
    invoice_date: str             = Field(..., description="Issue date (YYYY-MM-DD)")
    # ← invoice_date is str, not date! Flexible — some invoices have "Jan 15, 2024"

    supplier:    Party           = Field(...)
    # ☝️ Party instance = entire nested object. AI must fill ALL of Party's fields too!

    receiver:    Party           = Field(...)
    # ☝️ Same Party schema REUSED for receiver — clean DRY design.
    #    The descriptions guide the AI: supplier = seller, receiver = buyer.

    line_items:  list[LineItem]  = Field(...)
    # ☝️ list[LineItem] = 1 to N rows. An invoice for 50 products → 50 LineItem objects.
    #    Pydantic validates EVERY item in the list against the LineItem schema.

    vat:          list[VAT]       = Field(...)
    # ☝️ list[VAT] = multiple tax rates possible.
    #    E.g.: standard goods at 18% + medicines at 5% = 2 VAT entries.
    #    Each entry has its own rate, amount, and total.

✅ Party Reuse — DRY Design

  • One Party class handles both supplier and receiver perfectly
  • If you need to add a new field (e.g., vat_number), update in ONE place
  • This is proper OOP — define once, use many times

⚠️ Address Class is Unused!

  • Address is defined in invoice.py but NOT referenced inside Invoice
  • Party has its own duplicate address fields (street, city, state...)
  • Possible refactor: make Party contain an address: Address field instead

💡 invoice_date is str, not date

  • Unlike DriversLicense and Payslip, this uses str
  • More flexible — invoices often have formats like "Jan 15, 2024" or "15/01/24"
  • Trade-off: no auto-validation → parse manually if needed downstream
Section 06
⚠️ Gotchas & Best Practices

🚨 default=[] is a Bug

Never write field: list = Field(default=[]). That [] is shared across ALL instances — add to one, it appears in all. Always use default_factory=list. Pydantic will actually warn you if you forget.

⚠️ ... vs None vs 0.0 vs ""

These mean different things:
... = required, no default
None = not applicable / missing
0.0 = zero (was found, it's zero)
"" = empty string (found but blank)
Choosing wrong causes logic errors downstream.

⚠️ Field descriptions = AI prompts

The description= text in every Field() is included in the JSON Schema sent to the LLM. Vague descriptions → wrong extractions. Write them like instructions: "The seller's bank IBAN in format XX00..." not just "IBAN".

💡 float vs Decimal for Money

All money fields use float. In production, use from decimal import Decimal — floats have precision issues: 0.1 + 0.2 = 0.30000000000000004. For financial data, Decimal is the safe choice.

🔮 Docstrings Guide the AI

Class-level docstrings (the triple-quoted strings under the class name) are part of the JSON schema PydanticAI sends to the model. A well-written docstring like "Represents the SELLER/SUPPLIER details" helps the AI not confuse supplier with receiver.

✅ str | None vs Optional[str]

Both mean the same thing. str | None is the modern Python 3.10+ union syntax. Optional[str] (from typing) is the older style. These files use the newer | syntax — cleaner and easier to read.

⚠️ Literal must match exactly

Literal["invoice"] rejects "Invoice", "INVOICE", "invoices". Case matters. If the AI hallucinates a variation, the classification fails. Consider adding a @validator to normalise the string to lowercase first.

✅ Nested Models = Rich Context

Using list[LineItem] instead of list[dict] gives the AI much better guidance. The AI can see each LineItem field's name, type, and description — impossible with a raw dict. Typed nested models → better extraction accuracy.

🗂 Pydantic Fields Quick Reference

🔴 Required
field: str = Field(...)
Must be provided. No default. Missing = ValidationError.
🟢 Optional None
field: str | None = Field(None)
Can be missing. None means "not found / N/A".
🟡 Optional Default
field: float | None = Field(0.0)
Can be missing. Defaults to 0.0 (not none — zero).
🔵 Locked Values
Literal["a","b","c"]
Only these exact values accepted. Enum without Enum class.
🔮 List of Models
list[LineItem]
Array of objects. Each validated against schema. Use default_factory=list.
🩷 Annotated
Annotated[type, Field(...)]
Attach Field metadata to complex types like Literal[...]. Cleaner syntax.
