Section 01
🧠 Core Concepts You Need to Know
🔴

Synchronous (Blocking)

Your program calls a function and freezes until it gets a response. No other work happens. Like standing in line — you can't move until the person in front does. agent.run_sync() does exactly this.

🟡

Async / Await (Coroutines)

Python's async/await lets a function yield control while waiting for I/O. The event loop can run other coroutines in the meantime. But await agent.run() in a loop is still sequential — you await one-by-one.

🟢

asyncio.gather() — True Batching

asyncio.gather(*tasks) launches all coroutines at once and waits for all to finish. The event loop interleaves them during I/O waits. This is the sweet spot for API-heavy LLM calls.

🔵

Multithreading (ThreadPool)

ThreadPoolExecutor creates real OS threads. Each thread independently calls the LLM. Python's GIL is bypassed for I/O operations, making this effective. Good when your code isn't async-native.

🔮

Event Loop (asyncio)

The single-threaded scheduler at the heart of asyncio. It runs one task at a time but switches between them during await points. asyncio.run(main()) starts and manages this loop.

🧩

PydanticAI Agent

A structured AI agent wrapper. It handles prompt formatting, model communication, output parsing, and observability. Supports both run_sync() (blocking) and run() (async coroutine).

📡

Logfire Observability

logfire.configure() + instrument_pydantic_ai() automatically traces every LLM call — latency, tokens, model name — and sends to a dashboard. Essential for production monitoring.

🌿

dotenv + Environment Vars

load_dotenv(override=True) reads your .env file and loads API keys into os.environ. override=True means the file values win even if the var is already set in the shell.

🍕 The Restaurant Kitchen Analogy

Think of each LLM call as an order sent to the kitchen. Here's how each approach handles 10 orders:

🔴
Sync (a_sync) One waiter, one order at a time. Waits at the counter until dish arrives before taking the next order. Slowest.
🟡
Async Sequential (b_async) Waiter uses a walkie-talkie but still waits for each reply before calling again. Slightly better.
🟢
Async Batch (c_async) Waiter radios ALL 10 orders at once. Kitchen processes them in parallel. Picks up all at the same time. 🚀
🔵
Multithreading (d_mt) 10 different waiters, each handling one order independently. Parallel but more overhead per waiter.

File A
SYNC a_sync_llm_calls.py

The simplest approach — 100 LLM calls made one by one. Each call blocks the thread until the model responds.

a_sync_llm_calls.py
# ─── IMPORTS ───────────────────────────────────────────────────────────────
from dotenv import load_dotenv    # 📦 reads .env file → loads API keys to os.environ
from pydantic_ai import Agent    # 🤖 typed AI agent: wraps prompt/response/validation
import logfire                    # 📡 observability: traces every LLM call automatically
import time                       # ⏱ used to benchmark total execution time

# ─── SETUP ─────────────────────────────────────────────────────────────────
load_dotenv(override=True)       # override=True: .env values beat shell env vars
logfire.configure()             # initialise logfire with env credentials
logfire.instrument_pydantic_ai() # auto-patch Agent to emit spans (latency, tokens, model)

# ─── AGENT DEFINITION ──────────────────────────────────────────────────────
agent = Agent(
    'ollama:llama3-groq-tool-use:8b',  # 🏠 local Ollama model — no API cost, runs on your machine
    instructions="You are a helpful AI assistant",  # system prompt baked in
)

# ─── MAIN FUNCTION ─────────────────────────────────────────────────────────
def main() -> None:
    for _ in range(100):             # 🔁 loop 100 times — _ means "we don't need the index"
        res = agent.run_sync(         # 🚫 BLOCKING: thread freezes here until LLM responds
            "what is the capital of india. Just answer in one word"
        )
        print(res.output)             # .output = parsed/validated text from the model
    # ⚠️ Total time = sum of ALL 100 individual LLM response times (sequential)

# ─── BENCHMARK ─────────────────────────────────────────────────────────────
start_time = time.perf_counter()  # high-resolution timer — more precise than time.time()
main()
end_time = time.perf_counter()
print(f"Time taken(sync): {end_time - start_time:.2f} seconds")  # :.2f = 2 decimal places

⚠️ What's Happening

  • Each call blocks — call 2 can't start until call 1 finishes
  • 100 sequential waits = 100× single call latency
  • run_sync() internally runs its own event loop and blocks

✅ When This Is Fine

  • Scripts where you need ordered, serial processing
  • Debugging — easiest to trace errors
  • Very small number of calls (1–5)
File B
ASYNC SEQUENTIAL b_async_llm_calls.py

Async function, but still sequential. Awaiting one-by-one in a loop doesn't give you concurrency — it just uses the async interface.

b_async_llm_calls.py
from dotenv import load_dotenv
from pydantic_ai import Agent
import logfire
import time
import asyncio                    # 🔑 NEW: Python's async I/O framework

load_dotenv(override=True)
logfire.configure()
logfire.instrument_pydantic_ai()

agent = Agent(
    'ollama:llama3.1:8b',           # 📌 different model than file A (llama3.1 vs groq-tool-use)
    instructions="You are a helpful AI assistant",
)

# ─── ASYNC FUNCTION ────────────────────────────────────────────────────────
async def main() -> None:           # async def → this is a coroutine, not a regular function
    for _ in range(10):             # only 10 calls here (vs 100 in file A)
        res = await agent.run(     # await = "pause here, let event loop run other tasks"
            "what is the capital of india. Just answer in one word"
        )
        # ⚠️ BUT: there ARE no other tasks scheduled! So this is still sequential.
        #    await in a for-loop = one at a time. No parallelism gained.
        print(res.output)

# ─── ENTRY POINT ───────────────────────────────────────────────────────────
start_time = time.perf_counter()
asyncio.run(main())                # 🔁 creates a NEW event loop, runs main(), then closes it
end_time = time.perf_counter()
print(f"Time taken(Async-no batch): {end_time - start_time:.2f} seconds")

⚠️ The Big Misconception

  • Using async/await does NOT automatically make things parallel
  • Awaiting inside a loop = sequential. Same wall-clock time as sync.
  • You need gather() or create_task() to get real concurrency

💡 Why Use This Then?

  • You're in an async context (FastAPI, Discord.py bots, etc.)
  • The event loop is already running — can't use run_sync()
  • Stepping stone to understanding the async model
File C
ASYNC BATCHED ⚡ c_async_llm_calls.py

The async sweet spot. All coroutines are created upfront and gathered together — the event loop interleaves them during I/O waits for massive speedup.

c_async_llm_calls.py
from dotenv import load_dotenv
from pydantic_ai import Agent
import logfire
import time
import asyncio

load_dotenv(override=True)
logfire.configure()
logfire.instrument_pydantic_ai()

agent = Agent(
    'ollama:llama3-groq-tool-use:8b',
    instructions="You are a helpful AI assistant",
)

async def main() -> None:
    # ─── STEP 1: BUILD TASK LIST (no execution yet!) ────────────────────────
    tasks = [
        agent.run("what is the capital of india. Just answer in one word")
        for _ in range(10)
    ]
    # ☝️ agent.run() returns a coroutine object — NOT yet executed.
    #    This is a list of 10 "pending promises" ready to run.
    #    Think of it as 10 stamped envelopes not yet dropped in the mailbox.

    # ─── STEP 2: GATHER = run all concurrently ──────────────────────────────
    values = await asyncio.gather(*tasks)
    # ☝️ *tasks unpacks the list → gather(*[t1, t2, ... t10])
    #    gather() schedules ALL coroutines simultaneously on the event loop.
    #    When one await point is hit (waiting for HTTP response),
    #    the loop switches to the next coroutine. True interleaving!
    #    Wall-clock time ≈ max(individual times), not sum.

    print(*values)
    # ☝️ *values unpacks the results list → print(v1, v2, ... v10)
    #    values is a list of RunResult objects in original order (gather preserves order!)

start_time = time.perf_counter()
asyncio.run(main())
end_time = time.perf_counter()
print(f"Time taken(Async-batch): {end_time - start_time:.2f} seconds")

🚀 Why This Wins for I/O

  • All 10 HTTP requests to Ollama are in-flight simultaneously
  • Single thread — no thread-switching overhead
  • gather() preserves result ORDER regardless of completion order
  • Easy error handling: use return_exceptions=True

⚠️ Gotchas

  • If one task raises, gather() propagates immediately (unless return_exceptions=True)
  • Still single-threaded — CPU-heavy tasks won't benefit
  • Sending 100 requests may hit rate limits on remote APIs
File D
MULTITHREADING 🔵 d_mt_llm_calls.py

Uses a ThreadPoolExecutor with up to 100 real OS threads. Each thread independently makes a blocking LLM call. Python's GIL doesn't block I/O-bound threads.

d_mt_llm_calls.py
import concurrent                 # 🔑 concurrent.futures: high-level threading/multiprocessing
from dotenv import load_dotenv
from pydantic_ai import Agent
import logfire
import time

load_dotenv(override=True)
logfire.configure()
logfire.instrument_pydantic_ai()

agent = Agent(
    'ollama:llama3-groq-tool-use:8b',
    instructions="You are a helpful AI assistant",
)

# ─── WORKER FUNCTION (runs in each thread) ─────────────────────────────────
def run_agent(i):
    # i = task index (passed by executor but not actually used here)
    return agent.run_sync(          # run_sync is fine in a thread — each thread has its own stack
        "what is the capital of india. Just answer in one word"
    )
    # ⚠️ agent must be thread-safe for this to work reliably

def main() -> None:
    # ─── THREAD POOL ───────────────────────────────────────────────────────
    with concurrent.futures.ThreadPoolExecutor(max_workers=100) as executor:
        # max_workers=100: up to 100 threads can run simultaneously
        # 'with' block: threads are cleaned up automatically on exit

        futures = [
            executor.submit(run_agent, i)
            for i in range(100)
        ]
        # executor.submit(fn, arg) → schedules fn(arg) on a thread
        # returns a Future object immediately (non-blocking)
        # ALL 100 tasks are now queued/running concurrently

        results = [
            future.result()
            for future in concurrent.futures.as_completed(futures)
        ]
        # as_completed() → yields futures AS THEY FINISH (not in submission order!)
        # future.result() → blocks until that one future is done, then returns value
        # ⚠️ results list will be in COMPLETION ORDER, not original order!
        #    Use zip(futures, results) or dict if order matters.

    print(results)

start_time = time.perf_counter()
main()
end_time = time.perf_counter()
print(f"Time taken(Multi threading): {end_time - start_time:.2f} seconds")

✅ Strengths

  • Works with synchronous (non-async) code — no refactoring needed
  • GIL is released during I/O, so threads truly run in parallel for network calls
  • Good when using non-async SDKs or legacy code

⚠️ Watch Out

  • as_completed() returns in finish order — not submission order
  • 100 threads = high OS overhead; consider capping at 10–20 for most APIs
  • Thread safety: agent's internal state must be safe to share
  • Memory: each thread has its own stack (~1MB default on Linux)
Section 03
🌍 Real-World Use Cases
🔴 Sync

Simple CLI Tools

A command-line script that translates a document — one paragraph at a time, ordered output matters, no concurrent infra needed.

🔴 Sync

Pipeline Step

ETL pipeline where each LLM step feeds data into the next. Order & correctness matter more than speed.

🟢 Async Batch

Bulk Classification

Classify 1000 customer support tickets by category. Fire all at once with gather(), collect results in seconds.

🟢 Async Batch

Multi-Agent Pipelines

Run multiple specialized agents (summarizer, critic, formatter) in parallel on the same document, then combine outputs.

🟢 Async Batch

FastAPI Endpoints

Handle many simultaneous HTTP requests in an async web server — each request awaits the LLM without blocking others.

🔵 Multithreading

Legacy Code Integration

Adding LLM capabilities to a synchronous Django app or Celery worker without rewriting everything as async.

🔵 Multithreading

Stress Testing

Simulating 100 concurrent users hitting your LLM endpoint. ThreadPool makes it easy to model real concurrency.

🔮 Combined

Agentic Workflows

Outer async gather() for independent tasks; inner sync calls for tools that require sequential reasoning steps.

Section 04
⚠️ Gotchas & Best Practices
TopicGotcha / MistakeBest Practice
🔴 Async misconception async def + await in a for-loop is still sequential Use asyncio.gather() or asyncio.create_task() for true concurrency
🟡 Result ordering as_completed() returns futures in finish order, not submission order Use gather() if order matters, or map futures to original indices
🟢 Error propagation gather() raises on first exception by default, cancelling others Use asyncio.gather(*tasks, return_exceptions=True) for fault tolerance
🔵 Thread count max_workers=100 threads is often overkill — high memory + OS overhead Start with 10–20 threads; scale based on profiling, not guessing
🔶 Rate limits Firing 100 concurrent requests will hit API rate limits on OpenAI / Anthropic Use asyncio.Semaphore(10) to cap concurrent requests; add retry with backoff
🟣 GIL & CPU work Threading doesn't help CPU-bound Python code — GIL blocks parallel execution For CPU-heavy tasks, use ProcessPoolExecutor or offload to compiled code
⚪ override=True Forgetting override=True means shell env vars silently shadow .env values Always use load_dotenv(override=True) in dev; use real secrets manager in prod
🔐 Thread safety Sharing mutable state across threads leads to race conditions Keep agent calls stateless; use locks (threading.Lock) if shared state is unavoidable

🗂 Quick Decision Cheatsheet

🔴 Use Sync When
Small number of calls · Order matters · Debugging · Non-async codebase · Simple scripts
🟡 Avoid Async Sequential When
You have >5 calls · You want speed · You're already using async — use gather() instead
🟢 Use Async + Gather When
Many I/O-bound calls · FastAPI/async web server · Batch LLM jobs · Multi-agent parallelism
🔵 Use Threads When
Sync SDK only · Legacy integration · load testing · Mixed sync+async codebase
