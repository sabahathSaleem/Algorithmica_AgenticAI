🗺 The 4 Big Upgrades in This File

This is the most advanced agent file in the series — everything clicks together here

Previous files used static agent instructions set once at startup. This file introduces a dynamic instruction function that runs fresh on every single agent call, injecting runtime context (the company name) directly into the system prompt.

It also switches from asyncio.gather() to asyncio.create_task() for scheduling — a subtle but powerful difference that lets tasks start running immediately as they're created rather than waiting for a gather call.

1

🎭 @extraction_agent.instructions — Dynamic System Prompt

Instead of a static instructions="..." string, a decorated function runs on every agent call. It receives RunContext with the current deps (dependencies) and returns a fresh instruction string — personalised per call.

2

🔑 RunContext[str] + deps="TechNova Solutions"

ctx.deps holds whatever you pass as deps= in agent.run(..., deps="TechNova Solutions, Inc."). The type parameter [str] declares that deps will be a string. This is PydanticAI's dependency injection system.

3

⚡ asyncio.create_task() — Schedule NOW, gather LATER

Unlike building a list of coroutines and then passing to gather, create_task() starts the task immediately on the event loop as soon as it's called. Tasks run concurrently in the background while the for-loop continues creating more tasks.

4

📡 Logfire — Full Observability Stack

logfire.configure() + logfire.instrument_pydantic_ai() automatically traces every agent run: model called, tokens used, latency, input/output — all visible in the Logfire dashboard. Production-grade monitoring for free.

Section 01
🧠 Every New Concept Explained
🎭

@agent.instructions Decorator

Decorating a function with @extraction_agent.instructions registers it as the dynamic instruction generator. Every time the agent runs, it calls this function first to build the system prompt. The function receives RunContext as its argument.

🧒 Like: a coach who gives a different pre-game pep talk depending on which team they're playing tonight. The talk (instructions) changes per match (per call). Without the decorator — same talk every time.
🔑

RunContext[T] — Dependency Injection

RunContext[str] is a typed container that PydanticAI passes to your instruction function, tools, and validators during an agent run. ctx.deps holds whatever was passed as deps= in agent.run(). The [str] is the type of deps.

🧒 Like: a work order envelope handed to a worker when they start a job. Inside it says "this job is for: TechNova Solutions." The worker reads it and customises their work accordingly.
⚡

asyncio.create_task() — Immediate Scheduling

asyncio.create_task(coro) wraps a coroutine in a Task and schedules it on the event loop right now. The task starts running as soon as the current coroutine hits an await. Contrast with building a list of unawaited coroutines for gather.

🧒 Like: putting a pizza order in the oven right away vs collecting all orders first and putting them all in at once. create_task = in the oven now. gather pattern = wait, collect all, then bake together.
📡

Logfire Observability

logfire.instrument_pydantic_ai() monkey-patches PydanticAI's agent run methods to automatically emit structured spans — start time, model name, token counts, latency, input prompt, output — to the Logfire cloud dashboard. Zero manual logging needed.

🧒 Like: installing a black box recorder in a plane. Every flight (agent run) is automatically logged. If something goes wrong, you can replay exactly what happened and when.
🔒

deps= — Runtime Context Injection

agent.run(message, deps="TechNova Solutions, Inc.") — the deps parameter passes data into the agent run that is accessible in instruction functions, tool functions, and result validators via ctx.deps. Changes per call without changing the agent definition.

🧒 Like: a restaurant waiter who's told "Table 5's special guest is VIP — treat accordingly." The same waiter (agent), different instructions based on who the guest (deps) is.
🖼

image_paths[0] — First Page Only

pdf_to_jpg() returns a list of JPEG paths (one per PDF page). This file uses image_paths[0] — only the first page is sent to the AI. This assumes invoices fit on one page. If the PDF has multiple pages, the rest are silently ignored.

🧒 Like: scanning a stack of papers but only reading the top sheet. Fine if invoices are always 1 page — a bug if they're sometimes 2+ pages.
📋

invoices_filenames list — Tracking PDFs

The function maintains a parallel list invoices_filenames alongside tasks. This allows the caller to match each result back to its source PDF path. Since tqdm_asyncio.gather() preserves order, index 0 of results matches index 0 of filenames.

🧒 Like: keeping a numbered ticket for each coat you hand in at a cloakroom. When you get results back, you know which coat (PDF) belongs to which ticket (result).
💬

f-string in Dynamic Instructions

The instruction function returns an f-string: f"...for the company {ctx.deps}...". At runtime, {ctx.deps} is replaced with the actual company name. This means the system prompt itself is dynamically personalised — a form of prompt engineering at scale.

🧒 Like: a letter template with a blank for the recipient's name. Every time you send it, the name changes — but the rest of the letter stays the same.
Section 02 — Deep Dive
🎭 How RunContext + deps Flows Through the Agent
Data flows from agent.run(deps=...) → RunContext → dynamic instruction → system prompt
📞
Call Site
agent.run(
message,
deps="TechNova"
)
📦
RunContext created
PydanticAI wraps deps in RunContext[str] object. ctx.deps = "TechNova"
🎭
Instruction fn called
dynamic_instruction(ctx) runs. Returns f-string with company name injected.
🤖
System Prompt sent
GPT-4o receives personalised system prompt: "...for company TechNova Solutions, Inc."

Why is this powerful? You can call the same agent for hundreds of different companies in a loop — each call gets its own personalised system prompt — without creating 100 different Agent instances. One agent, infinite contexts.

💡 RunContext can hold any type

  • RunContext[str] — deps is a string (company name)
  • RunContext[dict] — deps is a dict with many values
  • RunContext[MyDataClass] — deps is a custom object
  • The type parameter is just for type checking — any picklable value works

✅ deps is also available in @agent.tool

  • Not just instructions — tool functions also receive ctx: RunContext
  • Use it to pass database connections, user IDs, API clients into tools
  • This is PydanticAI's dependency injection — like FastAPI's Depends()
Section 03 — Important Async Pattern Shift
⚡ asyncio.create_task() vs the Old Gather Pattern
🟡 Old Pattern — coroutines in a list
tasks = [
  run_inference(path)
  for path in image_paths
]
# ← coroutines created but NOT started

results = await asyncio.gather(*tasks)
# ← only NOW do they all start running
  • Coroutines created but sit idle until gather()
  • All start simultaneously at gather() point
  • Simple and predictable
  • Common pattern — easy to reason about
🟢 New Pattern — create_task() immediately
tasks = []
for pdf_path in pdf_paths:
    image_paths = pdf_to_jpg(...)
    task = asyncio.create_task(
        run_inference(image_paths[0])
    )  # ← STARTS NOW on event loop!
    tasks.append(task)

results = await tqdm_asyncio.gather(*tasks)
# ← waits for already-running tasks
  • Each task starts the moment it's created
  • Tasks overlap with the PDF-to-JPG conversion of next file
  • Event loop begins work immediately at first await
  • Slightly more throughput for mixed sync+async workflows

⚠️ create_task() needs a running event loop

  • asyncio.create_task() must be called from inside an async def function
  • Calling it at module level (outside async context) → RuntimeError: no running event loop
  • Here it's called inside async def extract_invoices_data() — correct!

✅ Both patterns produce the same final results

  • Order is preserved by tqdm_asyncio.gather() in both cases
  • create_task() may give marginal speed improvement in this specific loop
  • For pure IO-bound work without setup overhead, the difference is tiny

extractor_agent.py
# ═══ IMPORTS ══════════════════════════════════════════════════════════════
from pathlib import Path
from pydantic_ai import Agent, BinaryContent, RunContext
# ☝️ RunContext — NEW import! Carries runtime dependencies into instruction/tool fns
from pydantic_ai.models.openai import OpenAIChatModel
from pydantic_ai.providers.github import GitHubProvider
from pydantic_ai.models.groq import GroqModel
from pydantic_ai.providers.groq import GroqProvider
from pydantic_ai.settings import ModelSettings
from tqdm.asyncio import tqdm_asyncio
import asyncio
import os
import logfire                          # 📡 observability + tracing
from dotenv import load_dotenv
from models.invoice import Invoice       # 🧾 strict invoice Pydantic schema
from utils.utils import pdf_to_jpg, list_all_files
# ☝️ Imports from utils.utils → utils/ is a package (has __init__.py),
#    utils.py is the module inside it. "utils.utils" = package.module.


# ═══ SETUP ════════════════════════════════════════════════════════════════
load_dotenv(override=True)
logfire.configure()                    # connects to Logfire cloud (reads LOGFIRE_TOKEN from env)
logfire.instrument_pydantic_ai()       # monkey-patches Agent.run() to auto-emit traces
# ☝️ After this call, every agent.run() automatically records:
#    → which model was called
#    → how many tokens were used (input + output)
#    → total latency in ms
#    → the full prompt + response (optional, configurable)
#    All visible at logfire.dev dashboard — zero manual logging needed.


# ═══ MODEL SELECTION ══════════════════════════════════════════════════════
model = OpenAIChatModel(
    "openai/gpt-4o",
    provider=GitHubProvider(api_key=os.getenv("GITHUB_API_KEY")),
    settings=ModelSettings(temperature=0)
)
#model = GroqModel('meta-llama/llama-4-scout-17b-16e-instruct', ...)
# ☝️ Groq model is COMMENTED OUT this time — GPT-4o is active.
#    Opposite of generic_doc_agent.py where Groq was active.
#    Comment/uncomment the line to switch. Same "quick-swap" pattern.


# ═══ AGENT — No static instructions here! ════════════════════════════════
extraction_agent = Agent(
    model=model,
    output_type=Invoice,              # 🧾 AI must return a fully-structured Invoice object
)
# ☝️ Notice: NO instructions= parameter here!
#    Instructions are provided dynamically via the decorator below.
#    Static + dynamic instructions CAN coexist — dynamic ones are appended.


# ═══ DYNAMIC INSTRUCTIONS — THE KEY INNOVATION ════════════════════════════
@extraction_agent.instructions
def dynamic_instruction(ctx:RunContext[str]) -> str:
    # ☝️ @extraction_agent.instructions registers this function as the
    #    instruction generator. Called ONCE per agent.run() call.
    #    ctx: RunContext[str] → ctx.deps is a str (the company name)
    #    The [str] generic tells the type checker what deps will be.

     return f"""You are an AI assistant specialized in extracting information from invoice images for the company {ctx.deps}.
        Your task is to analyze the given invoice image and extract the relevant information.
        If a field is not present in the invoice or cannot be determined leave it as null.
        If the invoice date format is ambiguous, assume it's the international date format dd-mm-yyyy."""
# ☝️ {ctx.deps} is replaced with "TechNova Solutions, Inc." at runtime.
#    This makes the system prompt company-specific.
#    Call the same agent for a different company? Just pass a different deps= string.
#    The AI now "knows" which company it's extracting invoices for.


# ═══ run_inference — process ONE invoice image ════════════════════════════
async def run_inference(image_path: Path) -> Invoice:
    extractor_message_parts = [
        "Extract the structure from the provided document.",
        BinaryContent(data=image_path.read_bytes(), media_type="image/jpeg")
    ]

    try:
        print(f"##File analyzed: {image_path.stem}")

        extraction_response = await extraction_agent.run(
            extractor_message_parts,
            deps="TechNova Solutions, Inc."
            # ☝️ deps= is passed here at CALL TIME.
            #    This value flows into ctx.deps inside dynamic_instruction().
            #    The system prompt will say: "...for the company TechNova Solutions, Inc."
            #    To process invoices for a different client: change this string!
            #    In production: pass this as a parameter to run_inference() instead.
        )
        print(f"\n##Extracted data: \n{extraction_response.output}")

    except Exception as e:
        print(f"Unexpected error while inference: {e}")
        raise e     # re-raise original exception (prefer bare 'raise' in prod)

    return extraction_response.output   # validated Invoice Pydantic object


# ═══ extract_invoices_data — ORCHESTRATOR ════════════════════════════════
async def extract_invoices_data(invoices_dir:Path, temp_dir:Path):
    invoices_filenames = []   # tracks source PDF paths in same order as tasks
    tasks = []                # accumulates Task objects (already scheduled!)

    print('Extracting the invoices data')
    pdf_paths = list_all_files(invoices_dir)   # find all PDF files in directory

    for pdf_path in pdf_paths:
        print(pdf_path)
        invoices_filenames.append(pdf_path)      # track filename BEFORE creating task

        image_paths = pdf_to_jpg(pdf_path, temp_dir)
        # ☝️ This is SYNCHRONOUS — pdf_to_jpg blocks while rendering pages.
        #    The event loop cannot switch to another coroutine during this call.
        #    For production with many large PDFs, consider running in a thread pool.

        task = asyncio.create_task(run_inference(image_paths[0]))
        # ☝️ image_paths[0] → FIRST PAGE ONLY. Multi-page invoice detection is skipped.
        #    asyncio.create_task() → wraps coroutine in a Task and schedules it NOW.
        #    The task begins running as soon as the loop hits the next 'await'.
        #    It does NOT wait for the for-loop to finish before starting!
        tasks.append(task)

    invoices_result = await tqdm_asyncio.gather(*tasks)
    # ☝️ By this point, tasks are ALREADY running (started during the loop's awaits).
    #    gather() here means: "wait until all of them finish."
    #    tqdm wraps it with a live progress bar.
    #    Results preserved in SAME ORDER as tasks list → matches invoices_filenames.

    return invoices_filenames, invoices_result
    # Returns two parallel lists: (source PDF paths, extracted Invoice objects)
    # Caller uses zip(invoices_filenames, invoices_result) to match them up.
⚠️ Issue 1 — deps hardcoded inside run_inference()

deps="TechNova Solutions, Inc." is a string literal inside run_inference(). If you want to process invoices for a different company, you must edit the source code. Better pattern: pass company_name: str as a parameter to run_inference() and forward it to deps=.
✅ Better pattern:
async def run_inference(image_path: Path, company: str = "TechNova") -> Invoice:
    await extraction_agent.run(parts, deps=company)
⚠️ Issue 2 — image_paths[0] silently drops multi-page invoices

pdf_to_jpg() converts all pages, but only image_paths[0] (the first page) is sent to the AI. If an invoice spans 2+ pages, the additional pages are silently discarded. No error, no warning.
✅ Better pattern: Check len(image_paths) > 1 and log a warning, or loop over all pages and gather their extractions, then merge results.
⚠️ Issue 3 — pdf_to_jpg() is synchronous inside async loop

pdf_to_jpg(pdf_path, temp_dir) is a regular blocking function (uses Poppler, which is CPU/IO bound). Calling it inside an async def loop blocks the entire event loop during PDF rendering — other async tasks can't run while it's processing.
✅ Fix: Wrap in asyncio.get_event_loop().run_in_executor(None, pdf_to_jpg, pdf_path, temp_dir) to run it in a thread pool without blocking the event loop.
Section 04
⚠️ Gotchas & Best Practices

🩷 @agent.instructions vs instructions=

Static: Agent(instructions="You are...") — set once, never changes.
Dynamic: @agent.instructions def fn(ctx) — runs fresh every call.
Both can coexist — static runs first, then dynamic result is appended. Use dynamic when the prompt must change per call (company, user, session).

⚠️ RunContext[T] type must match deps=

If you declare RunContext[str] but pass deps={"name": "TechNova"} (a dict), PydanticAI won't crash at runtime — but mypy/pyright will flag the mismatch. Always match the generic type to what you actually pass in deps=.

🚨 create_task() needs a running event loop

Calling asyncio.create_task() outside of an async context (e.g., at module level or in a sync function) raises RuntimeError: no current event loop. Always call it from inside an async def function.

⚠️ print() inside tqdm tasks looks messy

Calling print() inside tasks that run under tqdm_asyncio.gather() will interleave with the progress bar, corrupting the terminal output. Replace with tqdm.write() which is tqdm-safe, or use a proper logger.

💡 Logfire adds latency — but worth it

logfire.instrument_pydantic_ai() adds a small overhead per agent call (sending trace data to Logfire cloud). Negligible for production LLM calls (which dominate latency anyway). For ultra-low-latency needs, configure logfire to use async export.

✅ Return type tuple is unpacked by caller

return invoices_filenames, invoices_result returns a tuple. Caller uses: filenames, results = await extract_invoices_data(dir, tmp). The two lists are parallel-indexed — filenames[i] is the PDF source for results[i].

🔮 Extending deps to a dataclass

For more complex context, use a dataclass: @dataclass class InvoiceCtx: company: str; user_id: str; db: Database. Then Agent(deps_type=InvoiceCtx) and RunContext[InvoiceCtx]. Access via ctx.deps.company, ctx.deps.db etc. Type-safe context injection at scale.

✅ utils.utils import path explained

from utils.utils import pdf_to_jpg — the first utils is the package (folder with __init__.py), the second utils is the module (utils.py file inside it). If the __init__.py was missing, this import would fail with ModuleNotFoundError.
