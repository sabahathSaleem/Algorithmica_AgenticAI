🧠 PART 1 — The Big Ideas (Concepts First!)

🧾 What is an Invoice? (The Real World Idea)

An invoice is basically a bill. When a shop sells you something, they give you a piece of paper (or email) saying: "Hey, you bought X, Y, Z — here's how much you owe us."

📦 Real life: You order a pizza. The receipt you get = an invoice. It has the pizza place's name, your name, what you ordered, price, taxes, and total.

🛡️ What is Pydantic? (The Bodyguard of Data)

Pydantic is a Python library that acts like a strict teacher for your data. You tell it "I want a number here, not a word" — and it enforces that rule automatically. If you try to sneak in wrong data, it yells at you with an error.

🏫 Real life: Imagine a school form that says "only write numbers in the Age box." If someone writes "twelve" instead of "12", the form rejects it. Pydantic does exactly that — but in Python code!

🏗️ What is BaseModel? (The Blueprint)

BaseModel is Pydantic's magic base class. When your class inherits from it, Pydantic automatically validates all the fields. You just describe the shape of your data — Pydantic does the checking!

🧱 Real life: Think of BaseModel as a Lego base-plate. Every model you build (like Invoice, Company) snaps onto it. Without the base-plate, your Lego castle falls apart!

🏷️ Type Annotations — Labelling Everything

In Python, you can add labels to your variables to say what type of value they hold. name: str means "name must be a text string." total: float means "total must be a decimal number."

🎒 Real life: You label your school bags — "Books bag", "Lunch bag", "Shoes bag". If you tried putting shoes in the Lunch bag — eww, wrong! Type annotations prevent that kind of mess in code.

🔬 Annotated + Field — Extra Rules on Top

Annotated[str, Field(...)] lets you attach extra rules to a type. Not just "this is a number" but "this is a number, AND it must be greater than 0, AND here's its description."

🎯 Real life: "Age" on a form is not just a number. The rules say: must be between 5 and 18 to join school. Field(gt=0) is like that — "greater than zero only!"

📌 Literal — Only These Exact Values!

Literal["incoming", "outgoing"] means the value must be one of these exact words. Nothing else is allowed. Not "Incoming", not "in", not 42 — only "incoming" or "outgoing".

🚦 Real life: A traffic light is only ever Red, Yellow, or Green. You can't have a "purple" traffic light! Literal works the same way — a fixed menu of allowed values.

🤖 Why Use This in AI / GenAI Systems?

When an AI (like Claude or GPT) reads a PDF invoice and extracts data, we need to guarantee the output is structured correctly. Pydantic models act as a contract: "AI, give me an Invoice object — or I'm rejecting your answer." This is called Structured Output or Extraction in GenAI.

🏦 Real life: Imagine hiring someone to read 1000 paper invoices and type them into a spreadsheet. Pydantic is the spreadsheet's column rules — it ensures every cell has the right kind of data before saving!

from typing import Annotated, Literal
# Annotated → lets us add EXTRA RULES to a type (like "str, but min 3 chars")
# Literal   → lets us say "ONLY these specific values are allowed"

from pydantic import BaseModel, Field
# BaseModel → the magic blueprint every model inherits from
# Field     → where we set rules like gt=0 (greater than zero), min_length, etc.

from datetime import date
# date → Python's built-in type for calendar dates (like 2025-01-15)
# Pydantic can auto-convert the string "2025-01-15" into a real date object!

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# 📦 MODEL 1: InvoiceItem
# Represents ONE line on a bill, e.g. "Web Design - ₹5000"
# An invoice can have MANY of these (that's why it's a list later)
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

class InvoiceItem(BaseModel):
    # Inheriting from BaseModel makes Pydantic auto-validate all fields below

    description: Annotated[str, Field(description="Item description")]
    # 🏷️  description → must be a string (text)
    # Field(description=...) → just adds a human-readable label (helpful for AI/docs)

    total: Annotated[float, Field(gt=0, description="Line item total")]
    # 💰 total → must be a float (decimal number) AND must be > 0
    # gt=0 means "greater than zero" — you can't have a negative item price!
    # If total=0 or total=-5 is given, Pydantic will REJECT it with an error
invoice.py — Company Model 
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# 🏢 MODEL 2: Company
# Represents a business — either the sender or the receiver of the invoice
# This model is REUSED twice inside Invoice (as issuer + recipient)
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

class Company(BaseModel):

    name: Annotated[str, Field(min_length=1)]
    # 🏷️  name → must be a string AND at least 1 character long
    # This prevents empty company names like name=""

    address: Annotated[str, Field(description="Full business address")]
    # 📍 address → just a string (no extra rules, any text is fine)

    phone: Annotated[str | None, Field(default=None, pattern=r"^\+?[1-9]\d{1,14}$")]
    # 📞 phone → can be a string OR None (meaning "no phone provided is okay")
    # str | None = Union type: "either a string OR empty/null"
    # default=None → if the invoice doesn't have a phone, just skip it
    # pattern= → a regex that checks the phone number format
    #   ^ = start, \+? = optional +, [1-9] = starts with 1-9, \d{1,14} = 1-14 digits
    #   Example valid: "+919876543210" or "919876543210"

    email: Annotated[str | None, Field(default=None, examples=["info@company.com"])]
    # 📧 email → optional (can be None), with an example for documentation
    # examples=[...] helps AI models and API docs understand what to put here
invoice.py — Invoice Model (The Big Boss!) 
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# 🧾 MODEL 3: Invoice — The Main Model
# This is the COMPLETE invoice — it nests Company and InvoiceItem inside it
# Think of it as the full pizza box that contains all the slices!
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

class Invoice(BaseModel):

    invoice_number: Annotated[str, Field(description="invoice number")]
    # 🔢 A unique ID for the invoice — like INV-2025-001 (just a string)

    invoice_date: Annotated[date, Field(description="invoice date")]
    # 📅 Must be a real date object — Pydantic auto-parses "2025-06-15" into date(2025,6,15)
    # You can't put "yesterday" or "soon" here — must be a proper date!

    invoice_type: Annotated[Literal["incoming","outgoing"] | None, 
                Field(description="""
    Set it to 'incoming' if the specified company is the RECIPIENT.
    Set it to 'outgoing' if the specified company is the ISSUER.
    Set it to None if the company doesn't appear on the invoice.""",
    default=None)]
    # 🚦 invoice_type has only 3 allowed values: "incoming", "outgoing", or None
    # Literal["incoming","outgoing"] = ONLY these two strings
    # | None = OR it can be empty/not known
    # 
    # 💡 This is super useful in GenAI:
    #    The AI reads the invoice and decides — is MY company paying or getting paid?
    #    "incoming" = money coming IN (we are the recipient, someone owes us)
    #    "outgoing" = money going OUT (we owe someone else)
    #
    # The long description= is literally the PROMPT given to the AI to fill this field!

    issuer: Annotated[Company, Field(description="The sending entity")]
    # 🏢 The company that SENT this invoice (nested Company model)
    # Pydantic will fully validate the Company sub-object too!

    recipient: Annotated[Company, Field(description="The receiving entity")]
    # 🏢 The company that RECEIVED this invoice (also a Company model)
    # Same Company blueprint, used twice — once for sender, once for receiver

    invoice_items: Annotated[list[InvoiceItem], Field(min_length=1)]
    # 📦 A LIST of InvoiceItem objects — every line on the bill
    # list[InvoiceItem] = "a list where each item must be an InvoiceItem"
    # min_length=1 → the invoice MUST have at least one item (empty bill = invalid!)

    subtotal: Annotated[float, Field(ge=0)]
    # 💰 Total before tax — ge=0 means "greater than OR equal to 0"
    # (unlike gt=0, this allows zero — a free invoice is still valid!)

    tax_rate: Annotated[float, Field(default=0, ge=0)]
    # 📊 The tax percentage like 18 for 18% GST — defaults to 0 if not mentioned

    tax: Annotated[float, Field(default=0, ge=0)]
    # 🏛️  The actual tax AMOUNT in money (subtotal × tax_rate / 100)
    # The AI or your code computes this; Pydantic just validates it's ≥ 0

    total: Annotated[float, Field(ge=0)]
    # 💵 FINAL amount = subtotal + tax — must be ≥ 0

    terms: Annotated[str | None, Field(default=None)]
    # 📝 Payment terms like "Net 30 days" or "Pay within 15 days"
    # Optional — many invoices don't have this, so None is the default
